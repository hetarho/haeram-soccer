## summary
- Two follow-ups merit implementation planning: record-level helper replication reduced own-match-day latency and CPU against today's helpers; a packed Wasm movement phase reduced isolated detailed-engine CPU. Production engine sources remain unchanged.
- Nine engine candidates, seventeen worker/transport configurations, six SIMD kernel cases and three direct current-helper comparisons were measured on an Apple M1 Max, Node v26.8.1. Complete results, rejected attempts, hashes, samples, source identities and current primary sources are in artifacts/benchmarks/engine-opt-261030/README.md, artifact commit 2a28f947 (available through origin/wip/eo30).

## findings
- F1 [o] P2 apps/web/src/runtime/helperPool.ts `HelperPool.run`, packages/engine/src/round-jobs.ts `simulateRoundJob`, packages/engine/src/world.ts `squad`: each helper receives a freshly parsed full read-copy object, losing its world-keyed generated-roster cache every round; growing the people/club registry also repeats serialization and transfer. Prototype ordered per-record replication, explicit snapshot revisions and a roster-input invalidation boundary. Against the shipped two-helper JSON path, four fresh processes × 120 paired days: own-match wall time ×0.9170 [0.8849, 0.9573], whole-process CPU ×0.8563 [0.7932, 0.9245], every daily world hash identical; total wall ×0.9862 [0.9477, 1.0262] is inconclusive. The prototype invalidated once per twelve batches instead of twelve times. ← ARCH-6/34: retaining an unchanged roster avoids repeated work without dropping fixture facts; plan failure/reload/stale-result handling, transfer/year-rollover parity and long-career scaling before adoption. Four-process evidence is exploratory; no overall elapsed-time or mobile claim. →T617
- F2 [o] P2 packages/engine/src/grid/movement.ts `advance` / `stepToward`: targets are fixed before the substep loop, but every substep repeatedly accesses mover objects and crosses scalar function boundaries. Keep a movement phase's finite numeric state in a contiguous slab, execute its existing f64 kinematics in Wasm and write back once, retaining the scalar callback-observed path. The 1,103-byte prototype passed ARCH-34's default grid comparison: 16 fresh processes × 18 reps, CPU ×0.9476 [0.9441, 0.9518], record hash 36c04541d86ef24c on both sides; 81,920 movement-value comparisons and complete observed outputs on two seeds also agree. ← ARCH-9/34: a focused numeric boundary improves this hot phase without a whole-engine rewrite; require feature detection, scalar fallback, generated-kernel maintenance, cross-browser/CPU parity and integration digests. The day workload hash agrees, but its own-day CPU interval [0.9459, 1.0075] includes 1: no whole-day improvement is claimed. →T618
