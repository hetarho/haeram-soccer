# REVIEW ui-engine-boundary-261027
> st:converted@261027 | scope:apps/web/src/ui runtime engine imports and the engine modules they name; ARCH-3/ARCH-4 layout and boundary wording; grid/aggregate internals excluded | at:6ef95e41 | base:ARCH@22

## summary
- The worker boundary itself holds: React never mutates the world, runtime host/protocol/slots reach no UI module, and the view publisher reaches no engine code. The coupling is at compile/import level: 53 UI source files import 39 engine modules whose runtime closure is the 137-module orchestration graph (world, season, match, grid/shape, transfers, managerMarket), and 81 UI source files reach world.ts transitively.
- Most of that reach is caused by constants, labels and one-line reads that live inside orchestration modules; 25 UI files reach the orchestration graph through a single such symbol. Nothing prevents a new UI file from adding another edge, and ARCH-3/ARCH-4 do not describe the real layout or say which engine modules the UI may name.
- Adopted: record the real layout and an engine read-leaf rule in ARCH, guard the current UI→orchestration edges with a shrink-only list, then move the label/constant/simple-read clusters into leaves. Real domain reads evaluated on the main thread (NPC squads, cost projections) need a measured decision and stay open.
