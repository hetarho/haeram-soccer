## goal
The game carries one version, 0.7.0: every package's `version`, `CURRENT_ENGINE_VERSION` and what the screens print as the rules version. A rules-4.0.0 checkpoint, parked game or import is the same rules line and loads as 0.7.0 with only its version label rewritten; everything older keeps today's legacy handling, and an unknown version is still refused.

## acceptance
- [ ] Root, `apps/web` and every `packages/*` `package.json` say `"version": "0.7.0"`; `CURRENT_ENGINE_VERSION` is `'0.7.0'` and its doc comment records that 0.7.0 continues the 4.0.0 rules line as the beta's first numbered version (SAVE-10).
- [ ] A world whose `engine` is `'4.0.0'` is accepted wherever a 0.7.0 one is (checkpoint load, parked slot, import, the worker and the read-only views) and is written back as `'0.7.0'` through the existing pure writer-activation transformation (→SAVE-10, SAVE-3); nothing else in it changes, and a read-only view never writes the upgrade.
- [ ] `LEGACY_ENGINE_VERSIONS` (1.x, 2.0.0, 3.0.0) keep their export-and-delete handling and their messages; a version that is neither current, 4.0.0 nor legacy is refused as from a newer game (→SAVE-11).
- [ ] Every place that prints the rules version (`earlierRulesMessage`, the new-career notice in `runtime/client.ts`, the slot screen) prints the game version; Korean copy reads `0.7.0`.
- [ ] Goldens and fixtures that store the engine version (`tests/fixtures/portable-v1.json`, `full-model-continuity.ts`, the legacy fixtures) are re-recorded or kept as 4.0.0 inputs on purpose, each with a one-line reason; the save-upgrade e2e covers a 4.0.0 save opening as 0.7.0.
- [ ] Tests: versions/persistence "a rules-4.0.0 checkpoint loads and is written as 0.7.0, its facts unchanged", "a read-only view loads a 4.0.0 save without writing it", "an unknown engine version is refused"; existing tests naming 4.0.0 as current move to 0.7.0.
- [ ] ARCH-30 task tier: typecheck, lint, format check and the changed unit tests pass; contract tests pass.

## impl notes
- The match-model revision IDs (`continuous-aggregate-N`) are unchanged: a revision ships inside a game version (T548's revision 7 is part of 0.7.0); no save migration of match records.
- `SUPPORTED_ENGINE_VERSIONS` becomes the current version plus the 4.0.0 alias the writer upgrades, never an open-ended older range (an arbitrary older semver is still not reset permission).
- Keep the 4.0.0 → 0.7.0 rewrite in one pure function next to the other activation steps so reading, importing and the worker share it.
