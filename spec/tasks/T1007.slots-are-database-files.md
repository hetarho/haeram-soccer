## goal
Each occupied slot is its game's database file: switching saves and closes the game in play and opens the next, a new game creates its file, deleting removes it, and the parked-envelope IndexedDB store is no longer used.

## acceptance
- [ ] `slots.park/continue` = `save` + `close-game`, then `open-game` of the next game ID; a failed open leaves both files untouched and reopens the previous game (SAVE-14).
- [ ] Starting a new game in a slot creates `/game-<gameId>.sqlite3` through `create-game` after the takeover; replacing an occupied slot (after its confirmation) deletes the old file first.
- [ ] `delete-game {gameId}` deletes the game's database (and, once T1010 exists, its backups) only after the existing confirmation (WEB-62); deleting the game in play reloads onto the slot screen as today.
- [ ] At startup a `list-games` answer (file names in the pool) makes slot-index entries without a file read as empty (SAVE-29); the IndexedDB `games` store is neither read nor deleted.
- [ ] Task stage, owner implementer: `vibe check --tier task` passes (`games.test.ts`, slot tests updated to the new flow); slot e2e journeys are a CI handoff.
