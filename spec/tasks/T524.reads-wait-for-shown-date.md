# T524 Reads during automatic play wait for the shown date
> st:todo | ssot:WEB-18 | base:WEB@162 | dep:T521 | touches:apps/web/src/runtime/client.ts apps/web/src/runtime/progression.ts apps/web/src/runtime/progression.runahead.test.ts | lane:- | explore:-

## goal
A read the engine answers outside the command queue never shows a day's results before the calendar shows that day: it first shows the days computed ahead and holds computing ahead until its reply lands.

## acceptance
- [v] Every client read that skips the command queue (`archive`, `recruitmentHistory`, `mediationPreview`, `personCareer`, `headToHead`, `clubRecords`, `managerHistory`, `leagueFixtures`, `fullStats`) is posted only after the progression controller has shown every held day at once, through the same path as office entry and hiding, so the controller's computed days and the client's held views stay in step.
- [v] An automatic step already in flight when the read starts lands and is shown before the read is posted; while the read is unanswered no step is computed ahead, and computing ahead resumes after its reply or error. A running clock keeps running: the read does not stop it.
- [v] With nothing held and no step in flight (manual mode, a stopped clock, a hidden tab) the read is posted at once as before.
- [v] `progression.runahead.test.ts` (unit, fake worker): with days held a head-to-head read reveals them before it is posted; a read started during an in-flight step is posted after that step is shown; no step is posted until the read's reply and the run then continues; a read with nothing held changes nothing. The existing run-ahead and `progression.test.ts` cases pass.
- [v] typecheck, lint/format on touched files and `pnpm exec vitest run --project unit apps/web/src/runtime/progression.test.ts apps/web/src/runtime/progression.runahead.test.ts` pass; `client.test.ts` (integration) updated if touched and listed in result limits.

## impl notes
- The client holds the views (`held`, `reveal()`); the controller holds the matching computed days and the clock (`flush()` = `reveal(true)`). Calling `client.reveal` from inside a client read would leave the controller's list behind: let the controller own the hook (for example a before-read callback it registers on the client that waits for an in-flight step, flushes and pauses computing ahead until the read settles).
- Reads skip the client's command queue but not the worker's message order, so a read posted behind an automatic step is answered after that step — hence waiting for the in-flight step first.
- Open views re-read when the shown day changes (RecordsRoom on `totalMatches`, TeamSheetDialog and LeaguePicker on `key`), so a records view left open during play shows the held days at once on each new result; that is the intended trade-off.

## result
- outcome: the nine reads that skip the command queue go through one client helper (`read`) that asks the controller's gate first; the controller registers the gate (`client.readGate`, cleared on dispose). While the shown clock runs or the owner's stop is still showing days, a read counts as pending, so `compute()` posts nothing. If a step is in flight (`computing`, the shown clock's step and its handling) the read waits for it to land. The controller then shows every held day at once through `flush()` (the office and hiding path), ends a draining owner's stop (unlock and save, SAVE-8), and only then lets the read be posted. When the read is answered or fails, computing ahead starts again at once. The clock keeps running throughout. Stopped, manual or hidden, the gate returns nothing and the read is posted at once, as before. The fake-worker cases check the read against the engine's head: posted at day 10 with 0 held, with nothing computed during a 2 s unanswered read and the run consecutive afterwards. With the gate disabled, 12 of the 13 new cases fail; the nothing-held case passes either way, as it should
