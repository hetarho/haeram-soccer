# T524 Reads during automatic play wait for the shown date
> st:todo | ssot:WEB-18 | base:WEB@162 | dep:T521 | touches:apps/web/src/runtime/client.ts apps/web/src/runtime/progression.ts apps/web/src/runtime/progression.runahead.test.ts | lane:- | explore:-

## goal
A read the engine answers outside the command queue never shows a day's results before the calendar shows that day: it first shows the days computed ahead and holds computing ahead until its reply lands.

## acceptance
- [ ] Every client read that skips the command queue (`archive`, `recruitmentHistory`, `mediationPreview`, `personCareer`, `headToHead`, `clubRecords`, `managerHistory`, `leagueFixtures`, `fullStats`) is posted only after the progression controller has shown every held day at once, through the same path as office entry and hiding, so the controller's computed days and the client's held views stay in step.
- [ ] An automatic step already in flight when the read starts lands and is shown before the read is posted; while the read is unanswered no step is computed ahead, and computing ahead resumes after its reply or error. A running clock keeps running: the read does not stop it.
- [ ] With nothing held and no step in flight (manual mode, a stopped clock, a hidden tab) the read is posted at once as before.
- [ ] `progression.runahead.test.ts` (unit, fake worker): with days held a head-to-head read reveals them before it is posted; a read started during an in-flight step is posted after that step is shown; no step is posted until the read's reply and the run then continues; a read with nothing held changes nothing. The existing run-ahead and `progression.test.ts` cases pass.
- [ ] typecheck, lint/format on touched files and `pnpm exec vitest run --project unit apps/web/src/runtime/progression.test.ts apps/web/src/runtime/progression.runahead.test.ts` pass; `client.test.ts` (integration) updated if touched and listed in result limits.

## impl notes
- The client holds the views (`held`, `reveal()`); the controller holds the matching computed days and the clock (`flush()` = `reveal(true)`). Calling `client.reveal` from inside a client read would leave the controller's list behind: let the controller own the hook (for example a before-read callback it registers on the client that waits for an in-flight step, flushes and pauses computing ahead until the read settles).
- Reads skip the client's command queue but not the worker's message order, so a read posted behind an automatic step is answered after that step — hence waiting for the in-flight step first.
- Open views re-read when the shown day changes (RecordsRoom on `totalMatches`, TeamSheetDialog and LeaguePicker on `key`), so a records view left open during play shows the held days at once on each new result; that is the intended trade-off.
