# T1010 Each game keeps a season backup and offers recovery from it

## goal
After each season close's save commits, and before a writer upgrade of rules, catalog or schema, the game file is copied to a backup; a corrupted database offers recovery from that backup, never automatically.

## acceptance
- [v] Backups alternate between `/backup-<gameId>-a.sqlite3` and `-b`; the slot index entry records which one is current with its season and game date; the new copy becomes current only after it is completely written, then the other is deleted (SAVE-31).
- [v] A season close is detected in the worker (year/season change between saves); its save commits first, then the backup is written; a writer upgrade (SAVE-10) writes the backup before saving the upgraded world.
- [v] Opening a game whose `PRAGMA integrity_check` is not `ok`, or whose rows fail to load for a reason other than compatibility, shows a recovery offer naming the backup's season and date and that later progress is lost, with export of the corrupted file first; accepting copies the backup over the game file, opens it and adds a 시스템 notification (WEB-66). An incompatible database is never offered this (SAVE-11).
- [v] Deleting a game deletes its backups (SAVE-14).
- [v] Unit tests with the node store cover backup rotation and the corrupted-open decision; the browser journey is a CI handoff.
- [v] Task stage, owner implementer: `vibe check --tier task` passes.

## impl notes
- Copy = `exportFile` of the game file after the commit + `importFile` into the backup name (T1005). For the node test adapter use `serialize` + a second in-memory database.
- Recovery UI reuses the existing recovery/error overlay (`App.tsx` RuntimeFeedback ~488-530, recovery export at 520); new copy via message IDs in every locale pack (AGENTS.md).
