## goal
The game in play's active checkpoint is written to IndexedDB (`haeram-soccor` / `checkpoints` / `active`) beside its previous copy instead of the synchronous localStorage key `haeram-soccor:slot:a`; a game still stored in localStorage loads and moves on the writer's first commit, and browsers without IndexedDB keep today's slot:a/b fallback.

## acceptance
- [v] With IndexedDB available a commit copies the committed checkpoint to `previous` (read back equal, skipped when the committed source is `previous`), writes the candidate to `active` (read back equal), and only then writes the manifest `{ slot: 3, worldId, generation, parentGeneration }`; the localStorage keys slot:a/b are removed only after that manifest write. No checkpoint string is written to localStorage on this path.
- [v] A failure at any of the three steps (a `write` that throws, a read-back mismatch, a quota error) rejects the save, leaves the committed generation and manifest loadable and reports no success (→ARCH-13); the 3 MiB conservative UTF-16 check (`CHECKPOINT_LIMIT`) still runs before any write.
- [v] Load: a `slot: 3` manifest reads `active`; a `slot: 0|1` manifest reads localStorage slot:a/b as today (the legacy layout and every existing e2e seed); without a valid manifest the newest valid of active, slot:a, slot:b and previous wins; previous is never brought back alone when no manifest, active or slot key exists. A read-only tab loads either layout and writes nothing (→SAVE-6).
- [v] Without IndexedDB the slot:a/b fallback, its 3.5 MiB budget and `PreviousUnavailableError` behave exactly as today.
- [v] Deleting the game in play (`forget`) and parking it (→SAVE-14) see the IndexedDB active copy: `forget` clears `active` and `previous` beside the localStorage keys; `committedRaw()` returns the committed checkpoint for every source without an async read; the recovery export (`rawBackup`) and App's "a game is stored" check before an import count an IndexedDB active copy.
- [v] Unit tests in `apps/web/src/adapters/repository.test.ts` with an in-memory active store beside `MemoryPrevious`: commit order and manifest `slot: 3`; legacy slot:a game moves on first commit and its keys are removed after the manifest; a throwing active write leaves the legacy/committed generation and manifest intact; load prefers the manifest's source and otherwise the newest valid; previous not recovered alone; no-IndexedDB fallback unchanged.
- [v] Existing persistence tests (`apps/web/src/adapters/persistence.test.ts`) pass with the IndexedDB layout where they construct a repository with a previous store; integration-tier cases are run by the host batch, not here.
- [v] e2e helpers that read the game in play's raw checkpoint after the app saved (`tests/e2e/club-identity-helpers.ts`, `tests/e2e/recovery.spec.ts`, `tests/e2e/save-upgrade.spec.ts` where it reads slot:a after a commit) read IndexedDB `checkpoints/active` when the manifest says `slot: 3`; seeds that write slot:a + a `slot: 0` manifest stay as they are (they exercise the move). The specs are listed in result limits for the host batch.

## impl notes
- Store: generalize `IndexedDbPreviousStore` in `apps/web/src/adapters/previousStore.ts` into `IndexedDbCheckpointKey` constructed with `'active' | 'previous'` (same `read` / verified `write` / `clear` on the existing `checkpoints` store through `idbRequest`, no DB version bump since the store exists); keep `IndexedDbPreviousStore` as the `'previous'` instance or replace its two uses. The `PreviousStore` interface in `repository.ts` is the port for both keys.
- Repository: new source constant `ACTIVE = 3` next to `PREVIOUS = 2`; `Source = 0 | 1 | typeof PREVIOUS | typeof ACTIVE`. The constructor takes an optional `active` store after `previous`; client.ts passes both only when `IndexedDbPreviousStore.available()` (one availability decision for both keys). Keep the committed raw in memory for the IndexedDB sources (generalize `recoveredRaw`) so `committedRaw()` stays synchronous; keep the raws read during `load` so `rawBackup` (client.ts) takes the recovery copy from the repository instead of reading localStorage itself.
- Writer (`checkpointWriter.ts`): the IndexedDB path no longer applies the localStorage total to `raw`; it checks only that the manifest fits. A first checkpoint (`committed === null`) still clears `previous` after commit, as today. Manifest `slot: 3` was chosen over reusing `slot: 0` so a legacy slot:a seed and the new layout are never confused (alt: `{ key: 'active' }`, which drops the lineage fields the load and e2e seeds read).
- Ordering inside one IndexedDB transaction is not required; the three verified steps in sequence already satisfy SAVE-3 (alt: one transaction for previous+active, a later optimization).
- The slot index (`haeram-soccor:games`), settings, device data and `legacyReset.ts` stay on localStorage; legacy rules ≤2.0.0 careers exist only in localStorage keys, so the reset needs no IndexedDB active handling beyond what `forget` does.
- Out of scope: the season-archive split, any change to codecs, budgets (`CHECKPOINT_LIMIT`, `TOTAL_LIMIT`, import limits) or autosave timing (SAVE-8), and the x10 match-day indicator (next planning slice of ideation save-storage-and-fast-pace).
- Tier: repository.test.ts is a unit file with small in-memory stores; run it plus typecheck/lint/format and `pnpm exec vitest run --project unit --changed`. persistence.test.ts cases that simulate worlds, `tests/e2e/recovery.spec.ts`, `save-upgrade.spec.ts`, the game-slot journeys seeded through `tests/e2e/slots.ts` and the storage benchmark belong to the host batch.

## result
- outcome: with IndexedDB the writer copies the committed checkpoint to `checkpoints/previous` (skipped when it is the recovered previous), writes and reads back `checkpoints/active`, writes the manifest `{ slot: 3, … }`, then removes slot:a/b; a slot:a/b game loads as before and moves on that first commit; without IndexedDB slot:a/b, the 3.5 MiB budget and `PreviousUnavailableError` are unchanged. `IndexedDbCheckpointKey('active' | 'previous')` replaces `IndexedDbPreviousStore`; the repository takes both keys or neither, keeps the committed IndexedDB raw in memory (`committedRaw()` stays synchronous) and the active copy it read for `recoveryRaw()` (client `rawBackup`) and `hasStored()` (App's import check through `client.hasStoredGame()`); `forget` clears active first (a failure keeps the game whole), then the localStorage keys, then previous. `idbRequest` now rejects a request refused synchronously instead of hanging.
