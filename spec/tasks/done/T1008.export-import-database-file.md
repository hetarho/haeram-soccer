# T1008 Export and import the gzip-compressed database as `.haeram-save`

## goal
Export writes `haeram-<club>.haeram-save` = header + gzip(database bytes); import checks it fully into a temporary file before it takes a slot; old `.haeram-save.json` files are refused as unsupported.

## acceptance
- [v] `saveFile.ts`: `encodeSaveFile(header, dbBytes): Promise<Uint8Array>` and `decodeSaveFile(bytes): Promise<{ header, dbBytes }>`; layout = ASCII magic `HRSAVE1\n`, one line of header JSON `{ format: 'sqlite-1', schema, engine, catalog, catalogHash, worldId, sha256, size }` and `\n`, then gzip of the database. Decoding refuses files over `PORTABLE_FILE_LIMIT`, stops gunzip at `DECOMPRESSED_LIMIT`, and checks size and SHA-256 before anything opens the bytes.
- [v] Import order (SAVE-9): header → limits → checksum → write to a temporary pool file → `PRAGMA integrity_check` = `ok` → schema/versions → `rowsToWorld` + world validation → only then becomes the slot's game file; any failure deletes the temporary file and leaves every slot untouched. A file without the magic (e.g. an old JSON envelope) is a `SaveCompatibilityError` with a localized message.
- [v] Export of the game in play saves first, then exports the file; per-slot export works for a game not in play; the download name keeps `haeram-<name>` with the `.haeram-save` extension, and the file inputs accept `.haeram-save`.
- [v] Unit tests (node driver, `DatabaseSync#serialize` for bytes): export → import round trip equals the world; truncated, wrong-checksum, oversize and JSON-envelope files are refused.
- [v] Task stage, owner implementer: `vibe check --tier task` passes; e2e specs that upload/download saves are updated (maintain only, CI) — list them in result limits.

## result
- outcome: A game exports and imports as a `.haeram-save` file. `adapters/saveFile.ts` (new) lays a file out as `HRSAVE1\n`, one header line `{ format: 'sqlite-1', schema, engine, catalog, catalogHash, worldId, sha256, size }`, `\n`, then the gzipped database (`encodeSaveFile(meta, dbBytes)`, `decodeSaveFile(bytes)`, `readSaveFileHeader`); decoding checks the magic (no magic — an old JSON envelope, another format number — is a `SaveCompatibilityError`, new copy `copy.saveFile.notSaveFile`), the header line, `PORTABLE_FILE_LIMIT`, the declared size against `DECOMPRESSED_LIMIT`, gunzips bounded at the declared size, then checks size and SHA-256, before anything opens the bytes. The worker has `export-game {gameId, memory?}` (the committed file's bytes behind a header read from the database's own `meta` rows, so a game of earlier or newer rules still exports untouched) and `import-game {gameId, replaces?, file}`: header → limits → checksum → scratch pool file `/import-<uuid>.sqlite3` → `PRAGMA integrity_check` = `ok` (copy.saveFile.integrity) → `sqlRecordStore` schema check → header against the database's meta → `storedWorld` (versions, catalog pin, `rowsToWorld` + `validateWorld`) + the writer upgrade it would get → only then the scratch file is removed, the bytes become `/game-<gameId>.sqlite3` (pool capacity reserved first, `importDb` never grows it), it opens as the game in play and the replaced slot game's file goes. Any failure removes the scratch file and leaves every file and the game in play as they were. The client exports the game in play after saving it (when that save fails, `memory: true` writes the unsaved changes into a copy of the committed file, so SAVE-3/SAVE-10's exportable in-memory progress stays); `GameSlots.exportFile(slot)` exports any slot (a game not in play as last saved) and `importInto(slot, bytes)` imports; `App.tsx` downloads `haeram-<name>.haeram-save`, reads uploads as bytes, and every file input accepts `.haeram-save`; the HUD's replace-and-import names the game in play as the one replaced. `DatabaseBytes` (read, meta, scratch, write) is the host's injectable byte port (OPFS pool in the browser, `node:sqlite` in tests, `tests/fixtures/save-file.ts`). 12 locale packs carry the 3 new messages.
