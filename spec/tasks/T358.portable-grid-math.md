## goal
The candidate detailed engine produces bit-identical records on linux-x64 and darwin-arm64 for the same inputs, so its facts no longer depend on the host's floating-point library (ARCH-5, ARCH-9).

## acceptance
- [v] `packages/engine/src/portable-math.ts` provides the transcendental functions the grid engine uses for outcome-critical values (at least `exp`, `atan2`, `sin`, `cos`; `hypot` too unless its bits are shown host-independent) built only from IEEE-754 basic operations (`+ − × ÷`, `Math.sqrt`, exact integer ops), with documented accuracy (max error in ulps over the grid's input ranges).
- [v] `portable-math.test.ts` holds recorded bit patterns (hex of the float64) for a fixed vector of inputs across each function's range, including edge values (0, ±tiny, large, the grid's pitch extremes), asserted exactly on every host; plus accuracy cases against `Math.*` within the documented ulp bound and a few properties (odd/even symmetry, `atan2` quadrants, `exp` monotonicity on the vector).
- [v] Every outcome-critical call in the grid engine's candidate path uses the portable functions; the pre-feature (default) path keeps `Math.*` so its golden facts are unchanged, with the selection made once per match rather than per call where speed needs it. Report the own-match cost change against T325's figures on this machine (interleaved, quiet window, a few runs) so T326/T286 see it.
- [ ] `grid-throughput.test.ts` and the candidate digest in `full-model-throughput.test.ts` are re-recorded for darwin-arm64 with a comment; after the coordinator's branch CI run, the same candidate facts digests hold on linux-x64, and the file records them as host-free again (the per-host split stays for the pre-feature path, if it still differs).
- [v] Statistics unchanged within noise: a paired candidate run before/after on one validation round (MATCH-29 rows, MATCH-23 core, MATCH-2 curve) shows no row moving from inside to outside; exact invariants hold. Task checks follow ARCH-30.

## impl notes
- Evidence: CI run 39800627501 (linux-x64, Node 24.22.1) gave a different facts digest for the candidate's observed 2024 shoot-out than this Mac (darwin-arm64, Node 26.8.1 and 24.18.0) for the same source (`work/q8m5` c2f5aa9), and observed trace/frames differ in the last bit on several fixtures (T325, T345 records). The 261020 suggestion (T271) saw the century world diverge between machines after 60 seasons. Same-Node-major runs on darwin match each other, so the host's float math (most likely V8's C++ `ieee754` functions compiled per CPU, with fused multiply-add on arm64) differs, and positions that evolve over thousands of steps compound it until a decision flips.
- JavaScript basic arithmetic and `Math.sqrt` are correctly rounded on every host, so functions written from them in a fixed operation order (range reduction + polynomial, e.g. fdlibm's algorithms transcribed to JS without fused operations) give the same bits everywhere and in a future Dart port. That meets ARCH-9's "specified representation … for cross-language replay" for coordinates without moving the engine to fixed point; if fixed point becomes necessary later, that is an ARCH question, not this task.
- Grid call sites (counted at c2f5aa9): `Math.hypot` 45, `Math.exp` 9, `Math.atan2` 5, `Math.sin` 3, `Math.cos` 3, in coordination, movement, decide, pitch, restarts, shape, playback, trace, resolve and tags. Presentation-only uses (`playback.ts`, `trace.ts` drawing) need not change; anything that feeds positions, distances, probabilities or draws does.
- The aggregate path's `Math.exp` uses (team.ts, participation.ts) compare a value against a fresh draw once per decision, so a last-bit difference flips an outcome only when a draw lands on the boundary; leave them and say so in `docs/MATCH-ENGINE-DESIGN.md`.
- T325's speed work matters (ARCH-31 budgets): keep the portable functions monomorphic and allocation-free, and avoid a per-call model branch in hot loops (for example bind the math table on the match state).
- Workers cannot see linux results: write the test so a mismatch prints the host and the actual hex values; the coordinator pushes the branch for CI and passes the result back.

## result
- outcome: The candidate grid's outcome-critical math reads only IEEE basic operations in a fixed order. (1) `packages/engine/src/portable-math.ts`: `exp` (e_exp.c), `log` (e_log.c), `tanh` (s_tanh.c with s_expm1.c), `sin`/`cos` (s_sin.c, s_cos.c, k_sin.c, k_cos.c, e_rem_pio2.c's medium Cody–Waite reduction; from 2^20·π/2 an exact `BigInt` reduction against 1,280 bits of 2/π computed by Machin's formula, its prefix fdlibm's `two_over_pi`), `atan2` (e_atan2.c, s_atan.c), `hypot` and `powInt` (whole powers multiplied out left to right), from `+ − × ÷`, `Math.sqrt`, `Math.abs`/negation and exact integer and bit operations (big-endian `DataView` words, a table of exact powers of two); every fdlibm constant is written as its bit pattern, and all 66 were checked against fdlibm's decimals. `hypot` was not left on `Math.hypot`: its V8 algorithm is basic operations in a fixed order (the portable one replicates it and matched it on 5,000,289 pairs, edge values included), but SpiderMonkey's and JavaScriptCore's differ, which CI 39815064804's Firefox/WebKit set-piece-defence failure showed (coordinator, mid-task).
