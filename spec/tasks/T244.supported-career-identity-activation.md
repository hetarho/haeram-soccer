## goal
Upgrade supported careers missing designs without changing their existing crests, game facts, history or read-only disk data.

## acceptance
- [v] An accepted supported-gameplay checkpoint with absent identities installs only missing defaults on activate+upgrade and reports that a validated candidate must be saved.
- [v] host.test.ts cases inspect/read-only activation does not install identities or increment revision, writer adoption preserves exact legacy crests and sporting facts, and repeat activation is a no-op pass.
- [v] If the existing rules/catalog upgrade already incremented revision, identity adoption adds no second increment; identity-only adoption increments once.
- [v] client.test.ts cases adoption commits through the existing save repository, failure preserves old raw data and export access, and slot import applies only to its intended world pass.
- [v] Missing historical appearances remain absent; unsupported older gameplay/future metadata continue their existing compatibility/reset rules and are not treated as identity migrations.
- [v] No main-thread storage write or rule-version change is added to a read-only path. Notices truthfully describe a save-data update instead of claiming a gameplay rule changed for an identity-only adoption.
- [v] Targeted verification passes: `pnpm exec vitest run apps/web/src/runtime/host.test.ts apps/web/src/runtime/client.test.ts apps/web/src/adapters/persistence.test.ts && pnpm run typecheck`.

## impl notes
- Read `docs/CLUB-IDENTITY-CONTRACT.md` sections named below; it owns the stable interfaces used in this task.
- Prerequisites: T243, T237, T236. Read their implemented interfaces/results before editing; extend those modules rather than reproducing a prerequisite.
- Read design §§3 and 6. Reuse decode, upgradeWorldRules and the EngineHost inspect/activation branch. Work on a cloned validated candidate, not the current canonical world or raw disk payload.
- Run installMissingIdentities only with both activate and upgrade. Its boolean participates in the existing upgraded reply and raw candidate encoding; do not put generation defaults into validateWorld or decode.
- Track whether the existing upgrade already changed revision. Guard safe integer overflow and increment once only when identity installation is the sole upgrade.
- GameClient.load and activate already decide writer ownership and commit upgraded raw through validation. Reuse that path and its failure/export behavior; do not bypass the post-grid previous-copy/manifest protocol.
- If the old notice says only 규칙 업그레이드, use truthful shared wording such as 저장 데이터를 현재 형식으로 갱신했어요. No new permanent banner or stopping acknowledgement is required.

## result
- outcome: completed. `EngineHost.execute('inspect')` (host.ts) keeps `decode` and `upgradeWorldRules` as they were; then, only when the request has both `activate` and `upgrade` (the writer's activation), it passes the result to a new private `adoptIdentities(world, revised)`. When some club lacks an identity, that function installs the missing defaults with `installMissingIdentities` on a `structuredClone` of the validated candidate, so the decoded world and the cached inspection are untouched. It moves the revision once only when no rules/catalog upgrade already moved it, refuses to move it past a safe integer (`저장 revision 범위를 초과했습니다.`), and returns the candidate itself when nothing is missing. The adopted world becomes the existing `upgraded` reply with its encoded `raw`, so `GameClient.load` commits it through the existing `saves.commit` (previous copy, then active key, then manifest), and explicit import or slot switch save it through the existing codec `save()`. Inspection, metadata-only and read-only activation (`upgrade` false) install nothing and write nothing; `validateWorld` and `decode` stay without defaults. Notices (client.ts): the success notice is now the exported `SAVE_DATA_UPDATED` (`기존 기록을 보존하고 저장 데이터를 현재 형식으로 갱신했어요.`), and the failure message reads `갱신한 저장 데이터를 저장하지 못했어요` instead of claiming a 규칙 업그레이드. This is true for both upgrade kinds, since only rules `4.0.0` are supported and the existing upgrade moves only a catalog pin. No new banner or stopping acknowledgement. Build: entry `index` 119.31 → 119.36 kB gzip, engine worker 1,997.64 → 1,997.92 kB raw, codec and settlement unchanged.
