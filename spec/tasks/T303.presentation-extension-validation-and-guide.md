## goal
Verify that registry/resource edits alone extend presentation while the deployed foundation still contains one locale and one theme.

## acceptance
- [v] Add `pnpm run validate:presentation`, reusing T299's shared validators to inspect both registries, their declared defaults/resources, message parameters and the required theme asset/era/stage/icon/font coverage. It reads registry data rather than maintaining another supported-ID list, and it reports the actual shipped entries without imposing a permanent one-entry limit on future additions.
- [v] Integrate presentation-resource validation with the existing static CI checks and local verify command. Detect missing local resource files, malformed defaults/duplicates, incompatible message parameters and missing required theme roles before deployment; do not add generated language/theme source imports or hand-maintained options to fix validation.
- [v] Unit cases in `validate-presentation.test.ts` cover `accepts a data-only added locale`, `accepts a data-only added theme`, `rejects a missing default resource`, `rejects inconsistent message parameters`, and `reports a missing era stage asset` using a temporary synthetic tree and injected contracts, without changing production pack counts.
- [v] Implement a responsive `presentation-settings.spec.ts` journey for default Korean/pixel labels, registry-derived settings before founding/on slots/in game, reload, denied preference storage and resource retry. A separate route-injected scenario appends synthetic locale/theme entries and responses: the existing settings discover/select them, common text/resources update, and game date, facts, drafts and stored Korean event prose remain unchanged. These fixtures are never registered or deployed as product packs.
- [v] Record the current production inventory as one locale (`ko-KR`) and one theme (`pixel`) in the result/guide. The browser fixture must demonstrate both an unknown-to-the-build locale and theme being loaded from registry/resource responses without importing a new TSX module or rebuilding a supported-ID list.
- [v] Write `docs/PRESENTATION-PACKS.md` with the registry and pack schemas, baseline paths, a generic add-pack procedure, parameter/fallback rules, semantic image/icon/font roles, configuration-file count and deployment/cache behavior. Explain that all source-copy extraction, production translations, new artwork and retrospective translation are separate work; app code is unchanged when adding a conforming pack, while new resources still must be deployed.
- [v] Task checks, the new resource validator and production build follow ARCH-30. Implement browser specs but leave actual execution to the pre-push batch and CI, naming the specs in result limits. Do not run the full suite or browser tests from this task.

## impl notes
- Validate every declared primary/alternative font resource through T301's shared source view and document ordered attempts. Static preview MIME support for the declared WOFF representation is delivery configuration; gameplay runtime/host implementations stay outside this task.
- Read runtime registries and reuse `validateRegistry`, `validateLocalePack`, `validateThemePack` and URL/slot resolution from T299-T301. Validation and the browser must agree on one contract; an independent second schema or language/theme enum would defeat the extension requirement.
- Use existing default image coverage and completed-stage semantics as the baseline. Test fixture assets can use tiny generated/in-memory resources; no new product artwork, fonts, additional language catalog or production registry entry is part of this task.
- Browser route injection models a resource-only deployment and keeps one production locale/theme. Check actual fetches and resource use, not only the presence of a new option. Avoid assertions that future pack additions require rewriting the test's fixed supported-ID list.
- The guide is the extension entry point: locale addition changes its registry plus JSON; theme addition changes its registry plus JSON and, if needed, one stylesheet, along with assets. It explicitly forbids per-pack TSX files, switches or feature-specific import lists.
- No runtime/host, save codec, match record, pitch or statistical feature implementation is changed. Existing full-model verification remains its own workstream.
