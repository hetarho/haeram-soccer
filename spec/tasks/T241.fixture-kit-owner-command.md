## goal
Add match-kit selection and automatic reset without applying a stale choice to a different fixture.

## acceptance
- [v] The command is {type: match-kit, fixtureId, role: home|away|third|null}; bridge and handler share the exact role vocabulary.
- [v] identity-operations.test.ts cases chooses for a league/cup/continental next own fixture, null restores automatic selection, stale/missing/settled/NPC fixture leaves the world unchanged, and choice does not edit saved shirt designs pass.
- [v] A manual role that clashes is accepted; the selector reports the warning independently. The engine must not turn the warning into a mandatory decision event.
- [v] The handler resolves nextOwnFixture at execution time across all competitions, not from the UI’s cached fixture list. Success increments revision only through operate.
- [v] host.test.ts verifies duplicate and stale request protections for this command; ordinary owner-decision autosave remains in effect.
- [v] Targeted verification passes: `pnpm exec vitest run packages/engine/src/identity-operations.test.ts apps/web/src/runtime/protocol.test.ts apps/web/src/runtime/host.test.ts && pnpm run typecheck`.

## impl notes
- Read `docs/CLUB-IDENTITY-CONTRACT.md` sections named below; it owns the stable interfaces used in this task.
- Prerequisites: T240, T239. Read their implemented interfaces/results before editing; extend those modules rather than reproducing a prerequisite.
- Read design §§2 and 5. Match the payload ID to nextOwnFixture(w).id before any write. A null role clears that named upcoming choice; otherwise store a copied {fixtureId,role}.
- Use the existing calendar helper, never a league-only w.fixtures[0] shortcut. A later cup draw may change which fixture is earliest, so a persisted valid named choice can survive until its own fixture settles.
- Use a precise stale-context error such as 다음 경기가 변경됐어요. 유니폼을 다시 골라 주세요. Do not catch that error and silently apply the role to the new next fixture.
- This task does not consume a choice or record a result; settlement owns that in the following task.

## result
- outcome: completed. `Command` adds `{ type: 'match-kit'; fixtureId: string; role: KitRole | null }`. The bridge takes it as a `z.strictObject` with `fixtureId: ref` (1–100 characters) and `role: kitRoleSchema.nullable()`, and the handler checks `role` against `KIT_ROLES`. `kitRoleSchema` is `z.enum(KIT_ROLES)`, so the bridge and the handler share one vocabulary. `chooseMatchKit(w, fixtureId, role)` in `identity-operations.ts` runs from an explicit `operate` case, which keeps its single `revision++` and its bankrupt refusal. Before any write it requires `nextOwnFixture(w)` — the calendar helper over league, cup and continental fixtures at execution time — to exist and have exactly that ID. Otherwise it throws the exported `KIT_FIXTURE_CHANGED` (`다음 경기가 변경됐어요. 유니폼을 다시 골라 주세요.`) and never moves the role to another fixture. A role stores a fresh `{ fixtureId, role }` in `World.kitChoice`. `null` deletes the stored choice only when it names that fixture, so a choice named for a later league match survives a cup tie drawn before it, as the impl notes ask. Because `World.kitChoice` holds a single choice, choosing a role for that new tie replaces the later match's choice. The handler writes no event, inbox item, design, cash or day, and a clashing role is stored like any other. `apps/web/src/ui/outcome.ts` (outside touches) gained the outcome title `다음 경기 유니폼을 정했어요`, which its exhaustive `Record<Command['type'], string>` requires.
