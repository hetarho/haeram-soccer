## goal
Expose the authoritative club-design tab with retained drafts, safe cancel/apply and immediate current-crest updates.

## acceptance
- [v] BUSINESS_TABS includes identity/구단 디자인 and /direction?view=identity; all existing/older business routes keep their meaning and ordinary tab return behavior.
- [v] Career drafts use useTaskState keyed by world ID, retain work across ordinary navigation, and clear on explicit discard/successful apply or a different game.
- [v] club-identity-management.spec.ts cases palette edits preserve all saved shirts, explicit reuse changes only the selected shirt, cancel and failed apply retain the correct values, and navigation detours restore the draft pass.
- [v] An apply uses exactly one club-identity command; current HUD/standings/team/slot crest summaries agree afterwards and survive reload.
- [v] Cases another slot never receives the draft, readonly can inspect but cannot apply, and a stale applied identity cannot be silently overwritten pass.
- [v] Ordinary date/revision changes under an unchanged applied identity do not discard or falsely invalidate the draft. The editor does not pause or start the clock on its own.
- [v] Targeted verification passes: `pnpm exec vitest run apps/web/src/ui/navigation.test.ts && pnpm run typecheck && pnpm run build`; `tests/e2e/club-identity-management.spec.ts` and `tests/e2e/owner-workflows.spec.ts` are written or updated here and confirmed by the batch Chromium run before the push (ARCH-30), named in `- limits:`.

## impl notes
- Read `docs/CLUB-IDENTITY-CONTRACT.md` sections named below; it owns the stable interfaces used in this task.
- Prerequisites: T240, T250. Read their implemented interfaces/results before editing; extend those modules rather than reproducing a prerequisite.
- Read design §7 and the actual post-grid business composition. Locate the component that owns BUSINESS_TABS (currently BusinessWorkbench); extend that owner, not the facilities, sponsor or strategy settings stores.
- Keep {entryIdentity,draftIdentity,worldId} in a game-scoped transient draft. Compare canonical current identity with entryIdentity for stale-owner-edit detection, not world.revision, which changes during normal automatic days.
- On apply, verify world ID and applied identity, await the existing GameClient.command result, and clear only after success. Error keeps the draft and provides retry/reload-current. A game switch while pending must not apply success UI to the new game.
- Cancel/되돌리기 is an explicit discard; merely opening another tab is not. Preserve the other operating-policy departments’ independent drafts.
- Add a documented identity field to any App world-projection selection list that would otherwise discard the new data; do not subscribe the entire UI to full career history.

The other views, older addresses and the first tab's bare `/direction` are unchanged. The page's ordinary return to the last tab (task-memory address plus `?view=`) needs no new code. `Operations.tsx` already passes every tab other than 운영 방침 and 재정 to `BusinessWorkbench`. That owner now takes `part: 'identity'` and renders a lazily loaded `ClubDesignView` (its own 3.71 kB chunk, sharing the `ClubIdentityEditor` chunk with founding). The view is keyed by world ID. The money views moved unchanged into a private `MoneyWorkbench`. New `ClubDesignView.tsx` keeps `{ worldId, entry, draft }` in `useTaskState(w.id, 'club-identity-draft', null)`. Task memory resets on another world, so another game never sees the draft. With no draft the controlled editor shows the applied identity (`identityOf`). The first edit starts a draft whose `entry` is a copy of the identity applied then. `clubDesignState` compares designs as `cloneIdentity` JSON, never by revision. A day's new projection of an equal design therefore leaves the draft standing. A different applied identity makes it stale: 적용 is disabled, and an alert offers 지금 적용된 디자인 불러오기 (explicit discard). Stale is suppressed only while an apply is in flight. A sticky top bar (the floating news button owns the bottom edge) shows the applied crest, a status (적용된 디자인 / 적용 전 초안 / 적용하는 중… / 읽기 전용), 되돌리기 (explicit discard, only with a draft) and 적용. 적용 sends exactly one `{ type: 'club-identity', identity: draft }` through the existing `GameClient.command` and awaits it. If another game is in play by the time it returns, it touches nothing. On success `afterApply` clears the draft, or keeps an edit made while queued as a new draft based on the sent identity. On failure the draft and the applied identity stay, and an alert offers 다시 적용 and 지금 적용된 디자인 불러오기. Read-only tabs show the design with the editor disabled (role/composer inspection stays open), a note that explains this, and a disabled 적용. A note states KIT-12 timing. The view never touches the clock. App's `selectContentWorld` needed no new key: identity rides inside `clubs`, already in every world-projection list, and the HUD, standings, team sheet and slot summary read it there. That is now documented beside `'clubs'`. `taskMemory.ts` needed no change. `navigation.test.ts` adds 5 cases: the tab list/route/older address, and the draft rules. Those cover applied vs draft and an edit taken back by hand; a reprojected equal design not stale and a newer one stale; another world's draft ignored; `afterApply` clearing or rebasing; and task memory keeping a draft for its world but clearing on another. New `tests/e2e/club-identity-management.spec.ts` (390x844) counts the club-identity commands the page actually posts to its engine worker through a `Worker.prototype.postMessage` wrapper. That wrapper can also make the next one carry an outdated revision, which the existing host check refuses. The spec decodes exported checkpoints and has six cases. (1) A palette and crest edit applies with 1 command: colours/crest change, `kits` equal before, `Club.color` is the new primary. Then 대표색 적용 on 원정 applies with the 2nd command and changes only `kits.away`. The new crest primary then shows in the HUD, the 리그 순위표 own row, its team sheet and the 슬롯 1 card, and after a reload. (2) 되돌리기 restores the entry value with 0 commands. A refused apply keeps the draft and the applied identity; 다시 적용 succeeds (2 commands). (3) Draft retained across the 시설 tab, a 선수단 page detour (the return lands on 구단 디자인), and running the clock until the date changes. It stays beside a 운영 방침 board draft, and after the identity apply that board draft is still there. (4) Slot 2's new game shows its own design with no draft, and back in slot 1 the draft is gone too. (5) A second, read-only tab inspects but cannot apply. (6) Importing the same game with a newer crest (built in Node from the exported checkpoint) makes the draft stale: the export keeps the newer identity, reload-current shows it, 0 commands.
