## result
- outcome: Completed: the new runtime/viewPublisher.ts holds the code moved out of host.ts: partText, VIEW_PATCH, isRecord, viewPatch and a ViewPublisher class. The class owns the retained `published` texts (seq, worldId, part JSON) and the view sequence, and its patch selection is the former Host.publish body. The only change is that publish takes the View as a parameter instead of calling this.view(). A missing View still returns {} before a sequence number is spent. Host keeps one ViewPublisher per instance. Its private publish(base) now builds its own View and passes it to `this.views.publish(view, base)`, so both reply paths are untouched. Host's public API is unchanged, and `export { VIEW_PATCH } from './viewPublisher'` keeps host.test's import working. PUBLISHED_VIEWS, View, ViewDelta, ViewPatch and applyViewDelta stay in protocol.ts, which needed no edit. viewPublisher imports only that protocol module, whose runtime closure is zod plus contract schemas. The new architecture guard pins the publisher's local apps/ closure to exactly protocol.ts and viewPublisher.ts, with no packages/engine file and no React or Zustand. No diff package and no wire-schema change were added. The six viewPublisher.test.ts cases use small prepared Views and rebuild each delta with applyViewDelta on a structured clone of the held view. They cover: a first view sent whole, per-publisher numbering, unchanged/changed/new/dropped parts and world keys, comparison by the JSON published even when a live object changes in place, a BigInt part that cannot be compared and is always sent, nested object and array patches (changed keys, removed keys, a new index, a shorter array), parts sent whole when small or when the patch exceeds maxShare, and full views for unknown, evicted and other-world bases.
