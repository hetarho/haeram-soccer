# T519 Helper workers for an own match day's other fixtures

## goal
On a day with our league fixture the browser computes the round's other fixtures on helper workers while the engine worker plays our match, with identical worlds and a sequential fallback.

## acceptance
- [v] `fixtureHelper.ts` is a worker entry running `simulateRoundJob` from T518; `helperPool.ts` (engine-worker side) splits a round's jobs across helpers, sends the read copy once per round as one JSON string, awaits results and returns them in fixture order.
- [v] The client creates `HELPER_CONFIG.count` helpers (2) only when `navigator.hardwareConcurrency >= HELPER_CONFIG.minCores` (4) and hands their ports to the engine worker, as it does for the codec (nested workers are not dependable, →ARCH-18). Creation failure, a helper error or a timeout (`HELPER_CONFIG.timeoutMs`) makes that round and later ones compute on the engine worker.
- [v] The host awaits helper results between the round's prepare and complete phases; commands stay serialized (→ARCH-6) and the step's reply is unchanged.
- [v] `helperPool.test.ts` (unit, fake ports): results return in fixture order whatever order helpers answer; a helper failure falls back and the world equals the sequential one; the pool is not used on days without our league fixture.
- [v] Day bench through the host path with helpers (Node worker_threads stand-in) keeps the world hash of the sequential run; interleaved ratio recorded in result (prototype: own match day 0.56–0.77×).
- [v] typecheck, lint/format on touched files and `pnpm exec vitest run --project unit apps/web/src/runtime/helperPool.test.ts` pass; `client.test.ts`/`host.test.ts` (integration) updated and listed in result limits.

## impl notes
- Prototype: `perf/integrated` `scripts/proto-parallel-fixtures/pool.mts`/`pool-worker.mts` (Node, synchronous `Atomics.wait`); the browser has no COOP/COEP, so use async messages, not SharedArrayBuffer.
- Use helpers only on own league match days: a day of other clubs' fixtures alone got slower with them (about 0.43 → 0.49 s) because the copy costs more than it saves.
- Two helpers suffice: our match is the critical path; four gave nothing more.
- Depends on T520 because both edit `client.ts`/`worker.ts`.

## result
- outcome: `helperPool.ts` holds `HELPER_CONFIG` ({count 2, minCores 4, timeoutMs 8000}, type-only engine imports so the client entry loads no engine), `HelperPool` (contiguous shares across ports, one `JSON.stringify` of the read copy per round posted to each helper, results in job order; an error reply, a short reply, a timeout, an unserializable copy or a throwing port disables the pool and resolves `undefined`, so that round and every later one compute on the engine worker; it never throws into `prepareRound`) and `playDay(pool, w, observe, steps)` (engine steps injected: `prepareRound` → helpers run while our match plays → `completeRound(results)`; any other day, or no active pool, is `advanceDays(w, 1)` at once). `fixtureHelper.ts` is the module worker (`answer`/`serve`, entry only under `WorkerGlobalScope`, like codec.ts). The client creates the helpers when `navigator.hardwareConcurrency >= minCores`, posts each a channel port and hands the other ends to the engine worker (`{type:'helpers', ports}`); a creation throw sends nothing, a helper `error` terminates them and posts `{type:'helpers-failed'}`; `dispose` terminates them. The host's `advance-days`/`next-match` loop steps each day through `playDay`; while an own match day waits for its helpers, reads (head-to-head etc.) wait for the completed day (`afterRound`), commands stay on the serialized queue, and the reply is built exactly as before.
