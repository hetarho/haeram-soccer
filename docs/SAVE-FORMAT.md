# Portable v1 save format

The envelope carries schema `2` (`3` for a world carrying match-model data, `4` for one carrying own-manager history), engine/catalog IDs, catalog hash, world ID, generation, parent generation, codec, SHA-256 checksum and payload. Payload losslessly compresses UTF-8 canonical compact JSON. The checksum covers the uncompressed canonical compact JSON, not the envelope or compression implementation.

## Checkpoint container schema

The envelope `schema` is the checkpoint-container version (`CURRENT_CHECKPOINT_SCHEMA`, `SUPPORTED_CHECKPOINT_SCHEMAS` in `packages/contracts/src/versions.ts`), separate from `World.schema` and the worker protocol, which both stay `1`. Container `2` is written once club identities exist (→SAVE-20): its fields, codecs, checksum, catalog pins and accepted rules are those of container `1`; only the number differs, so a reader that knows only container `1` refuses a design-bearing save instead of silently dropping its identity fields.

- Old reader (container `1` only): a container-2 checkpoint is an unsupported schema, a typed compatibility failure that keeps the raw save for export; it never falls back over it to an older checkpoint.
- Current reader: reads containers `1`, `2`, `3` and `4`. A container-1 checkpoint loads as it is and is never rewritten while reading; the next commit writes the container its world needs (`checkpointContainerFor`, below), and the container-1 predecessor stays as written. No container admits earlier gameplay rules (→SAVE-19).
- Container `4` (`MANAGER_HISTORY_CHECKPOINT_SCHEMA`, →SAVE-24, HIST-18) is written for exactly the worlds that carry own-manager history (`World.managerHistory` or any `MatchRecord.managerTenure`), with or without full-model data: `checkpointContainerFor` (`apps/web/src/adapters/managerHistoryPacking.ts`) picks it from `carriesManagerHistory` and otherwise falls back to `checkpointSchemaFor`. A container-4 world may also carry T402's model metadata, aggregates and record models unchanged. `readCheckpoint` refuses history in containers `1`–`3` and a container-4 payload without it as compatibility failures, never corruption, and container `4` is no evidence of earlier rules for the legacy reset. A reader that knows only containers `1`–`3` refuses it instead of dropping the facts.
- Any other container is a compatibility failure, checked before decompression: the selected raw checkpoint and manifest are preserved, no older checkpoint is loaded or written over it, and its header's engine is not taken as evidence of an earlier-rules career (`envelopeEngine` returns nothing for it), so it never qualifies for the legacy reset.
- After the checksum and bounded JSON decoding, `assertIdentityFormatVersions` runs on the payload's world (`compact1.world`) before unpacking: a club identity or match appearance with a positive integer `version` above `1` is a compatibility failure, not corruption. Malformed current-version data still fails ordinary validation.
- Container `3` (`FULL_MODEL_CHECKPOINT_SCHEMA`, →SAVE-23) is written for exactly the worlds that carry full-match-model metadata (`World.matchModel`), current-season NPC aggregates (`World.npcSeason`) or a full record (`MatchRecord.model`): `checkpointSchemaFor` (`packages/contracts/src/match-model.ts`) picks it from `carriesMatchModel` and keeps container `2` for every other world, so an unactivated career's checkpoints are unchanged and an older reader refuses a model-bearing save instead of dropping its fields. Its envelope fields, codecs, checksum, catalog pins and accepted rules are those of container `2`. Writing container `3` only follows data already in the world: a career gets it from the writer's activation (below) or from a founding with the release switch on, and keeps it on every later checkpoint, export and import.
- Full-model activation boundary (→SAVE-23, T402): the model is recorded once, by the writer tab's validated activation (`inspect` with `activate` and `upgrade`, after the rules and identity upgrades) while the release switch `MATCH_MODEL_RELEASE` is on, and only on a rules-4.0.0 world carrying no model data. It stores `matchModel` with the activation's game date and the revision of the first checkpoint carrying it, `trackedFrom` (the first game day and league round not yet lived) and `coverage` (`founding` for a world with no settled round or own match, else `activation`), plus an empty `npcSeason` counting from that boundary; settled records, tables, money, dates, people and history are written unchanged and nothing before the boundary is backfilled. The activated world is the next checkpoint, in container `3`, committed through the ordinary protocol below; a failed commit keeps the previous checkpoint and leaves the activated career exportable. Activation waits while the career's live world holds an own match the checkpoint being loaded lacks (a queued or revealed playback ahead of disk), so that fixture replays under the model it was settled with. Read-only tabs and inspections never activate or write. Loading follows the recorded model whatever the switch says: a container-3 career loads and plays on its model with the switch off, and the switch decides only whether an unactivated career is activated. The same writer activation also starts own-manager tracking (container `4`, below), so a container-3 career saves in container `4` from then on with its model data unchanged.
- After unpacking, the declared container must match the payload: model data in container `1` or `2`, or a container-3 payload without any, is a compatibility failure (`SaveCompatibilityError`), not corruption, because no writer this version knows produces it, so it is kept for export and never recovered over. A container-3 header is no evidence of earlier rules: `recognizedLegacy` is false for it, so it never qualifies for the legacy reset. A rules-4.0.0 career, with or without the model, is never legacy-reset data.
- `assertMatchModelFormat` (`packages/contracts/src/match-model.ts`) is the bounded preflight for model data inline in a world: a `matchModel.revision`, `npcSeason.model` or `ownMatches[*].model` string other than a known `MATCH_MODEL_REVISIONS` entry throws `SaveCompatibilityError`; missing metadata is the pre-feature model and passes. `readCheckpoint` runs it on `compact1.world` beside `assertIdentityFormatVersions`, then `readMatchModelFormat` on the payload's `model` section, both before unpacking, and `validateWorld` runs it before Zod. The world schema accepts supported `matchModel` (strict), `npcSeason` (strict, record-width rows) and record `model`.

Codec `gzip-cjk14` (written when gzip is at most 1,200,000 bytes) encodes the gzip bytes as dense text: a header character U+4E00 + p, where p (0–13) is the number of zero padding bits, then one character U+4E00 + v per big-endian 14-bit group v (U+4E00–U+8DFF, CJK Unified Ideographs: assigned, no surrogates, stable under every normalization form). Browser storage is budgeted per UTF-16 code unit, where Base64 carries 6 bits and this text 14. Decoding rejects characters outside the range, a padding count above 13, a bit length that is not a whole number of bytes and non-zero padding. Codec `gzip-base64` (standard Base64 of the same gzip bytes) is still read; it is never written.

Large checkpoints use `brotli-bmp127`: Brotli quality 11/window 24, then blocks of at most 127 bytes interpreted as unsigned big-endian integers and written as exactly 64 base-63198 digits (leading zeros included). The digit alphabet is U+0100–U+D7FF followed by U+E000–U+FFFD, excluding U+FDD0–U+FDEF. A header U+4E00 + n gives the final block's byte count (1–127); n=0 is valid only with no blocks. Reject unknown characters, partial blocks, invalid headers, numbers exceeding the declared block width and payloads exceeding the byte limit before decompression. Unlike CJK14, this is opaque verbatim text and must never be Unicode-normalized. One full block occupies 128 conservative UTF-16 bytes per 127 compressed bytes.

The pinned `brotli` 2.1.0 encoder is static JavaScript; separate lazy encoder/decoder imports run under the existing CSP without WebAssembly or eval. The committed pnpm patch enforces output limits before initial/growth allocations and caps the decoder window at 24; input and output remain bounded by the 32 MiB inflate limit. Window 24 also keeps the bounded input within one encoder window; every candidate is decoded and checksum/schema-validated before storage. Large compression is slower than gzip and remains in the background codec worker; its response deadline is ten minutes, separate from the one-minute engine snapshot deadline. An export of the already committed current revision returns that same validated envelope; unsaved recoverable memory still uses the normal encoder/checksum path.

Canonical JSON sorts object keys by raw UTF-16 order, retains array order, drops undefined object fields, uses finite JSON numbers and encodes exact money as decimal strings. It rejects unsupported values. The complete inflated representation must fit 32 MiB; imports cap 8 MiB; a stored checkpoint is at most 3 MiB conservative UTF-16 and namespaced localStorage use at most 3.5 MiB. Header, version, checksum, world schema, references, currency and pinned catalog hash are checked before activation.

## Lossless compact representation

`apps/web/src/adapters/packing.ts` is the reference codec. `compact1` keeps current world metadata, a shared string dictionary, owned-match tuples, binary statistics and standings counts. It omits reproducible domestic fixture definitions: reconstruct with the pinned engine's `prepareSeason(world, false)` and apply saved score tuples by fixture index. European fixtures remain explicit.

Match tuples preserve fixture identity/year/round/kind/home/away/country/group/score, owned player IDs, recorded highlights and tactics. Numeric streams use column-transposed unsigned LEB128 without truncation. Current encoding groups actor dimensions, player IDs, highlights and tactics into separate streams; the reader also accepts the former combined actor stream and older explicit match tuples.

Statistics use declared-width bit columns: width 156 for uniform 11-player owned matches (13 rows × 12 counters), otherwise width 12. Exact per-column minima and bit ranges preserve all safe integer bits. The optional `planes` layout groups equivalent bit positions for gzip; omitted layout retains the earlier column interpretation. Optional residual flags encode failed passes/off-target shots and signed interception-versus-tackle differences. Decode restores the original counters; unsafe values, unknown layouts, truncated streams, invalid dimensions and unconsumed data fail validation.

Domestic and European phase standing rows each have width 6, stored in a separate column-transposed unsigned-LEB128 stream with optional signed column deltas. Per-season domestic row counts and per-tournament first/second phase counts reconstruct every row. Event templates and variable-string dictionaries preserve complete event details. String dictionaries and tuples are bounded; unused/missing stream elements fail decoding. No pruning or lossy rounding is allowed.

Seasons closed under rules `1.12.0` or later also archive what their pages need after the live tables are gone. The own league's ten leading scorers (name, club index, role, goals, appearances), the own rank after every league round and the rounded Club Elo spread (world lowest, world highest, own league lowest, own league highest) stay inline in the history JSON. Each knockout bracket (`cup` for the own country's cup, otherwise the continental competition key; the Super Cup is not kept) keeps its rounds from the first round of 32 clubs or fewer to the final: label, league round, legs and bye club indexes stay inline with an empty tie list, while every tie row of every season — [home, away, leg 1 home goals, leg 1 away goals, leg 2 home goals, leg 2 away goals, outcome], each leg in its own fixture's order, 0, 0 for a single match's leg 2, outcome = winner side (0 home, 1 away) + 2 for penalties + 4 for away goals — shares one width-7 column-transposed unsigned-LEB128 stream (`bracketTies`). `bracketCounts` holds, per season, each archived round's tie count in order; counts that disagree with the archived rounds or with the stream's row count fail decoding (`대진 기록 압축 데이터 손상`), as does a stream without archived brackets. Seasons closed earlier have none of these fields and are never backfilled.

Rules `1.13.0` worlds may carry two optional fields inline in the world JSON: `buildNext` (a strategy reserved for the next season: its build cards and an optional name of at most 20 characters) and `managerMarket` (`year` and `round` of the last refresh, `free`: at most eight free-agent managers in the manager shape, `clubs`: per club that changed manager the pair [count, since], and `serial`, the number of free agents created). Other clubs' managers are derived from the seed, the club and its count, so only changes are stored. Earlier worlds have neither field.

Rules `1.14.0` changes no field. Continental knockout rounds drawn from then on put a tie's return leg (`:2`) on its era's calendar instead of the next round; legs stored earlier keep their rounds, and stage labels read both calendars.

Rules `1.15.0` adds one optional field inline in the world JSON: an outgoing (`out`) bid may carry `offer`, the market player it was made for in the player shape with the asking `fee` and `loanFee` as decimal strings, so the bid is answered on those terms whatever the market list shows meanwhile. A bid pending from earlier rules has no `offer` and finds its player in its season's list as those rules did. The rest of `1.15.0` changes results, not fields: every progression mode lives the same days in one order with draws named by what they settle (each day lived advances `revision` by one, so a league round is as many revisions as its days), the amateur level swaps places with the last professional division by the amateur table, a currency change converts every live amount and market lists follow the settings. Checkpoints from `1.0.0` through `1.14.0` remain accepted.

Rules `1.16.0` add, among others, three optional fields inline in the world JSON for the owner's levers, each stored only while it differs from its default: `hiring` (`manager`: the manager criteria `minOvr`, `schools`, `minFlexibility`, `maxPride`, `minYouth`, `traits`, an optional `maxWageOvr` of 50–90 in steps of 5, `priority`, `term`, `poach` and `whenNone`; `coaches`: per department the coach criteria `volunteer`, `minAbility`, an optional `trait`, an optional `maxWageOvr`, `priority` and `term`), `talkRule` (`maxPay` one of 0.9, 1, 1.1, 1.25 and 1.4, `minOvr`, an optional `maxAge` of 28–40) and `buildChanged` (per strategy slot, the `year` and `day` its card last changed; the slot stays locked for 90 days from then, and only running locks are kept). Delegation keys `coach:<department>` replace the single coach-hiring key `staff`. `buildYear` and `buildNext` are read only from older worlds: a load turns `staff` into the seven department keys with its value and drops `buildYear`, so every slot is free; it turns coaching investment levels (`coaching`) into `hiring.coaches` entries where none exists (1 → `volunteer: true`, 2 → nothing, 3 → `minAbility: 65` with `priority: 'ability'`, each over the defaults) and drops `managerRule`; writer activation drops `buildNext` with an inbox item naming it and delegates contract talks where the academy is delegated.

Rules `4.0.0` adds own-match facts and season heat maps. Each has an optional stream written only when some match or season carries the field, so a world without them packs exactly as before; every field stays absent when absent (never an empty value).

- `matchExtras`: one row of width 11 per own match (a column-transposed unsigned-LEB128 stream, row count = `matchCount`): `[flags, lineCounts home, lineCounts away, added 0, 1, 2, 3, regulation home, away, shootout home, away]`. Flag bits: 0 `lineCounts`, 1 `added`, 2 `added` has four entries (otherwise two; bit 2 requires bit 1), 3 `regulation`, 4 `shootout`, 5 `incidents` present (also when empty), 6 `material` present. Values of fields whose bit is clear must be zero. It is written when any match sets a flag.
- `matchIncidents`: `counts` (width 1, one count per own match, zero when the incidents flag is clear, at most 120) and `rows`, a width-7 `planes` bit-column stream with one row per incident in match and time order: `[minute, added + 1 (0 = none), side, kind index, player ref, other ref + 1 (0 = none), reason index + 1 (0 = none)]`. Kind order: `yellow`, `secondYellow`, `red`, `sub`, `injury`. Reason order: `reckless`, `tactical`, `dissent`, `dogso`, `serious`, `violent`. Player refs index the shared string dictionary.
- `matchMaterial`: `lengths` (width 4: lengths of `shots`, `heat`, `network`, `report`, one row per match whose material flag is set) and four width-1 bit-column streams `shots`, `heat`, `network`, `report` holding those arrays of all flagged matches concatenated in match order.
- `seasonHeat`: `counts` (width 1, one value per archived season: 0 = no `heat`, otherwise players + 1) and `rows`, a width-41 `planes` bit-column stream `[player ref, 40 cell counts]`, players in object order within a season. The packed world's seasons carry no `heat`.
- Widened team and player advanced counters (31 and 24 columns, `TEAM_DETAIL_SIZE`, `PLAYER_DETAIL_SIZE`) need no new stream: they flow through `matchDetail`, whose bit columns take their widths from those constants. Matches with substitutes (more than 11 own lines) use the existing `statWidth` 12 / `playerWidth` 1 path.
- `discipline` and `Fixture.shootout` of cup and European fixtures live in the inline world JSON. Streams that disagree with the match or season count, with their flags or with their dictionary, or that leave data unread, fail decoding.
- Measured size (T232, rules 4.0.0): the largest 100-season checkpoint is 2,382,876 of the 3,145,728 conservative UTF-16 bytes, with `matchDetail.players`, `statBits`, the career `jobs` and `matchIncidents.rows` its largest streams; no codec change was needed (docs/VERIFICATION.md).

Club identities (container `2`, →SAVE-20/22) add no world stream: `Club.identity` and the pending `World.kitChoice` stay inline in the packed world JSON. Own-match appearances, which the column rebuild of `ownMatches` would drop, use one optional side channel `appearances: { version: 1, values, refs }` (`apps/web/src/adapters/identityPacking.ts`):

- `refs` has one entry per own match in record order: `0` = no appearance (the record keeps none, never `null`, an empty object or today's colours), `n` = `values[n - 1]`. `values` holds each distinct snapshot once, interned by its canonical JSON in first-occurrence order, with literal colour spelling kept; refs therefore introduce `1, 2, …` in order and every value is used.
- It is omitted when no record has an appearance, so a world without them packs exactly as before, and earlier `compact1` payloads read unchanged.
- Reading checks before expanding anything: a positive integer stream or snapshot `version` above `1` is a compatibility failure (`SaveCompatibilityError`), checked first so damage elsewhere is not reported as corruption for a newer game; any other version, more than 100,000 values or more values than records, a ref count other than the record count, a negative, fractional, out-of-range, skipped or unused ref, a duplicate value, a value failing the strict appearance schema, or sides other than the rebuilt record's home then away fail decoding. Each record receives its own copy of its snapshot.
- Measured (one simulated season, seed `identity-command`): 32 own matches, 31 distinct snapshots, 15,505 canonical characters of side channel; the encoded checkpoint grows from 66,587 to 67,235 characters. Storage budgets, retained history and movement frames are unchanged.

Match-model data (container `3`, →SAVE-23, HIST-17) leaves the packed world JSON: `matchModel` and `npcSeason` are removed from `compact1.world` (a payload with either inline fails decoding) and every record's `model` would be dropped by the column rebuild, so all three travel in one optional section `model` (`apps/web/src/adapters/matchModelPacking.ts`), omitted when the world carries none so containers `1` and `2` pack exactly as before:

- `version: 1` and `revisions`: each model revision the section names, literally and once (1–16 entries). Refs below are indexes into it.
- `state` (with `matchModel`): `[revision, activated.year, activated.day, activated.revision, trackedFrom.year, trackedFrom.day, trackedFrom.round, coverage]`, coverage `0` = `founding`, `1` = `activation`.
- `records` (when any record has a model): runs `[ref, length, …]` over the own records in order, ref `0` = no model (the record keeps none), `n` = `revisions[n - 1]`; lengths are at least 1, adjacent runs differ and the lengths sum to the record count.
- `season` (with `npcSeason`): `header` `[year, revision, trackedFrom.year, day, round]` and four sparse tables, rows in the original order. `competitions` `[kind, groupKey, club rows, player rows]` (kind index into `league, cup, europe, playoff, lower`); `clubs` `[club, matches, xg, xga, metrics(12), detail(TD 31)]`, the competitions' club rows in turn; `players` `[id, name, position, contribution rows]`; `contributions` `[club, appearances, starts, metrics(12), detail(PD 24)]`, each player's shares in turn. Club, group, player ID, name and position strings are refs into the payload's shared `dict`; counters keep their canonical units (xg/xga in hundredths, xtAdded in thousandths).
- A sparse table is `{ rows, columns }` with one entry per column: `[values]`, a `planes` bit column of all rows, or `[presence, nonzero]`, a 0/1 bit column per row and a `planes` bit column of the nonzero values in row order. The writer takes the presence form only when it needs fewer bits; a zero is stored as zero, never omitted, and an empty competition keeps its row with zero counts.
- Reading checks before anything is rebuilt: a section `version` above `1` or an unknown revision is a compatibility failure, checked first; any other version, an empty, oversized or duplicate revision table, an unused revision, a state or header of the wrong width, a ref out of range, a malformed run, a table whose row or column count differs from its declaration, a presence value other than 0/1, a nonzero count that differs from the presence count, a stored zero among the nonzero values, truncated or padded bit data, leftover rows, more than 1,000 competitions or clubs per competition, more than 100,000 players per competition, a player with no or more than 50 shares, and a duplicate ledger key (a competition `kind` and `groupKey`, a club or player within a competition, or a player's club) fail decoding. Ranges of the rebuilt values stay with the world schema.
- Departed, retired and transferred players keep their rows under their stable IDs: the section never consults a roster. A supported container-1 or container-2 world has no section and loads with every historical counter genuinely absent, never zero.
- Measured (synthetic, not settled football: ENG founding after 20 rounds, 24 scopes, 467 club rows, 8,406 single-club players with mostly-zero counters): the encoded checkpoint grows from 96,487 to 189,250 characters. The century workload with real aggregates is T286's gate; no field is pruned and no limit is raised.

Own-manager history (container `4`, →SAVE-24, HIST-18/19) leaves the packed world JSON as well: `managerHistory` is removed from `compact1.world` (a payload with it inline fails decoding) and every record's `managerTenure` would be dropped by the column rebuild, so both travel in one optional section `managerHistory` (`apps/web/src/adapters/managerHistoryPacking.ts`), omitted for a career not yet tracked so earlier containers pack exactly as before:

- `version: 1` and `header` `[club, tracked year, day, revision, coverage, serial]`, coverage `0` = `founding`, `1` = `activation`.
- `tenures`: 14 columns per tenure in appointment order, `[manager, person + 1, name, interim, tracked year, day, appointed year, day, known since, ended year, day, departure + 1, appointment key, departure key + 1]`. Departures are indexes into `replaced, resigned, retired, expired`; an absent date is `0, 0` and an absent ref, year or departure `0`. Tenure IDs are not stored: the `n`-th tenure is `<club>:tenure:<n>` (`managerTenureId`).
- `outcomes`: 12 columns per outcome in settlement order, `[kind, year, tenure index, at year, day, …source]`, where a league finish's source is `[country, tier, group]`, a cup title's `[competition]` (`cup` or the continental tournament key, the Super Cup included) and a promotion's `[club, from country, tier, group, to country, tier, group]`; unused source columns are `0`.
- `records` (when any record has a link): runs `[ref, length, …]` over the own records in order, ref `0` = unattributed (the record keeps none), `n` = the `n`-th tenure; lengths are at least 1, adjacent runs differ and the lengths sum to the record count.
- Strings (club, manager, person, name, appointment and departure keys, competition and country codes) are refs into the payload's shared `dict`; dates keep their exact `{year, day}` and counters their integers.
- Reading checks before anything is rebuilt: a section `version` above `1` is a compatibility failure, checked first; a header or row of the wrong width, a ref out of range, a nonzero unused column or absent-date day, a tenure index or record ref past the tenures, a malformed or short run, a duplicate outcome source and a record section that links nothing fail decoding as corruption. The rebuilt facts then pass T304's strict `managerHistoryFactsSchema`, and `validateWorld` refuses facts of another club and a record naming a tenure the facts lack.
- Writer activation and coverage: a new career tracks from its founding (`coverage: 'founding'`, the founding manager appointed on day 0). A supported older career starts tracking once, at the writer tab's validated activation (`Host.adoptManagerHistory`, after the rules, identity and model adoptions): `coverage: 'activation'`, `trackedFrom` today with the activated revision, the manager in charge as the first tenure with his known first season as `knownSince` and no appointment date. Matches, outcomes and events before the boundary stay unattributed, never inferred from names or dates. Activation waits, like the model's, while the live world holds an own match the checkpoint lacks. Read-only tabs and inspections never track or write. Tracking is independent of the match-model release switch and never changes model metadata.
- Measured (T308, `docs/benchmarks/manager-history.json`, rules 4.0.0 on an M1 Max): both century profiles track from the founding and stay within SAVE-4 with every fact, date and link round-tripping exactly. The baseline century checkpoint is 2,442,012 and its settled round after the century 2,540,444 of 3,145,728 conservative UTF-16 bytes (2 tenures, 109 outcomes, section 3,682 canonical / 427 brotli bytes). The active-management century is 2,120,222 and its round 23 2,221,470 (32 tenures with 11 interims, 4 managers appointed twice and 10 same-day appointments, 107 outcomes, section 5,401 / 806 bytes). No field is pruned and no limit is raised.

Archived movement frames are not save facts. Historical goal playback uses preserved goal minutes; only the final recorded counters are displayed in that summary playback.

Scorer records keep one stable player identity through transfers within the tracked league. An optional `clubs` array retains actual `{club, goals, appearances}` contributions once more than one club contributes; live records use club IDs and archived top-ten records use stable club indexes. Aggregate totals must equal those contributions, each club occurs once, and the displayed club is the latest contributing one. Older single-club records remain valid without an invented split.

## Second-career feature state

The rules 3.0 feature payload keeps settings (seven responsibilities, progression mode and observations), the recruitment support row, player qualities, staff/manager person links, joint playing-coach proposals, coaching-market refresh dates, actual recruitment arrivals, mediations and promises as canonical fields. The envelope, checksum, two-slot protocol and size limits are unchanged. Release activation and bounded legacy classification are separate from this encoding.

`compact1.careers` is optional and independently versioned. The retained version-1 reader accepts `{ version: 1, people: [...] }`. When present it is the only encoded person-registry source; `world.people` is absent. Each person is one strict 20-column tuple:

1. Shared-dictionary indexes for ID/name; birth year; position index; professionalism; understanding/teaching/judgement grades; playing-status index.
2. Optional club index, optional former-own boolean, optional origin `[club, slot]`, optional loan `[parent club, until]`, and genuinely retained own-career metrics.
3. Employment rows `[role, club, from year, from day, to year, to day, contract-end year, contract-end day, wage, currency, grown-through year]`.
4. Mentor rows `[manager, name, school, club, from year, from day, to year, to day]`.
5. Optional intention `[year, day, retained draw, willing, encouragement year, encouragement day, changed]`, retirement `[announcement year, announcement day, scheduled year, actual year, actual day]`, coaching `[role, actual ability, potential, entry year, entry day]`, and management `[actual ability, potential, school, entry year, entry day]`.

Identity, club, role, school, name and exact decimal-money strings use the existing shared dictionary. Null means absent, preserving false/zero values; dates require both columns together. Learned ability/potential retain finite numeric precision. Player/staff arrays and their stable person links remain inline, preserving qualities and role-specific facts without a second complete person object. All employment and mentor periods survive; missing playing totals stay absent.

The writer uses career version 3, retaining the version-two relationship grammar implemented by `careerColumns.ts` and the exact order restoration described below. It owns a separate string dictionary and transposes the same facts into 18 person columns (the version-1 columns excluding employment and mentors), 11 employment columns, per-person job counts and mentor lists. Neither records nor numeric precision are discarded. Names may reference an exact first-space split; origin-based person IDs may reference exact `p` or `vacancy` templates. Every nonmatching string stays literal. The declared seed must match the containing world.

Employment flags (bits 0–8) indicate end, contract end, equal end/contract, exact two-calendar-year contract, wage, currency, growth year, current coaching-role reference and calendar reference. Absent/reference cells are zero and are checked. Literal start years are relative to the preceding employment's end/start year, or bounded birth year; endpoints and growth years use their declared date anchors. Exact wages use sorted year/currency books and per-person rank deltas; decimal spelling, including leading zeros, survives. Club references rank available clubs in the explicit sorted non-own-club vocabulary by role. Events order by start/end date with endings first, then raw person ID and original job index. Overlapping, own-club and otherwise unmatched records use literal club references. This is reversible referencing, not simulation.

Mentor profiles are grouped by club. An interval matching an existing employment exactly references its job index relative to the mentor index and its local profile. All other intervals retain literal club and endpoints. Person, employment and mentor array order remains unchanged.

Version 2 freezes its scalar codebooks: FNV-1a (2166136261, multiplier 16777619) and xorshift32 (13, 17, 5, zero state replaced by one) yield unsigned draws divided by 2^32. Exact aptitude matches to `seed:aptitude:person` with weights 8/22/40/22/8 use three null markers; exact first `seed:coaching-intention:person` draws use null. Other exact unsigned 32-bit fractions use a true marker and four Base64 byte planes, least significant first; arbitrary fractions stay literal. Unused plane bytes must be zero. No mutable gameplay generator is imported.

The explicit sorted calendar stores foreign non-player start dates as `year * 366 + day`, preserving raw day 365 even in non-leap seasons. Exact start dates may reference their rank among dates at/after the previous end, coaching entry or bounded birth anchor for which the first frozen `seed:coaching-market:person:year:day` draw is below 0.25; otherwise the literal date remains. At most 16 Mi calendar probes are allowed; the encoder falls back to literals when exhausted and the decoder rejects excess work. Row counts cap at one million, expanded person/job cells at 16 Mi, and dimensions, flags, dictionaries, pools, books, descriptors and references are checked before the unchanged strict career/world validation. A future career version remains a typed compatibility failure.

The decoder accepts prior `compact1` worlds with an inline registry and no `careers` section. It rejects simultaneous inline/row registries, unknown career-row versions, malformed dimensions or dictionaries, duplicate identities and invalid expanded references/intervals/deadlines. Schedule reconstruction never enrolls people, draws career facts or changes the saved registry. Full canonical save/export/inspect state stays complete; daily UI projections omit lifetime people and bound resolved decisions, with on-demand reads for full details. Drafts and derived display models are not canonical save fields.

## Commit and recovery

Application keys: `haeram-soccor:slot:a`, `haeram-soccor:manifest`, and the previous committed checkpoint in IndexedDB (database `haeram-soccor`, store `checkpoints`, key `previous`). The manifest selects the current slot/world/generation and parent generation. A commit copies the committed checkpoint to IndexedDB and reads it back, writes/readback-verifies `slot:a`, switches/readback-verifies the manifest, then acknowledges; a failure before the switch leaves the committed generation loadable. Without IndexedDB the active and previous checkpoints alternate between `slot:a` and `slot:b` (write/readback-verify the inactive slot, then the manifest) while both fit the 3.5 MiB budget; when they do not, the commit is refused before any write with `previous-unavailable`, keeping the committed checkpoint and in-memory progress for export/retry. A two-slot layout still loads and moves to IndexedDB on its next commit, removing `slot:b` after the manifest switch.

Validate the manifest's slot, world ID, generation and parent generation against the selected checkpoint. A valid manifest selects the committed generation even when an interrupted write left a newer inactive slot. A valid previous-generation compatible checkpoint (the other slot or the IndexedDB copy) may recover the previous world after corruption. Corrupt/missing manifests trigger recovery in descending generation order, with slot A, then slot B, then the IndexedDB copy winning a tie; the IndexedDB copy is never read when no manifest or slot remains. Unsupported selected schemas, engine versions or catalogs are compatibility failures: preserve and export the selected raw career instead of silently falling back to an older one. Loading/recovery does not erase source slots. Export uses the same envelope and can preserve in-memory progress when browser quota prevents a new checkpoint.

Only one Web Lock owner writes. Commands use protocol/session/request/expected revision; duplicate effects are prevented by acknowledgments/receipts and stale revision checks. Main-thread adapters perform storage I/O; the worker validates, projects, compresses and hashes.

Engine rules `1.1.0` accept `1.0.0` careers. Writer activation upgrades only engine metadata, the catalog pin of a save written under an accepted earlier catalog, and revision through a pure transformation and the two-slot protocol; old match/player/economic facts and absent optional fields remain unchanged. Read-only views do not upgrade metadata or disk. Upgrade write failure keeps the old committed career and exportable upgraded memory, with an explicit retry. Unsupported versions/catalogs require an explicit future migration or matching engine. No legacy Flutter JSON importer or automatic downgrade is claimed.

Rules `4.0.0` start new careers. Only known released rules `1.0.0`–`1.22.0`, `2.0.0` and `3.0.0`, with a readable container schema (`1` or `2`) and recognized catalog/codec, a `compact1` payload whose world header matches the envelope, and a valid checksum, qualify for the writer-only legacy gameplay reset; recognition reads only the envelope and that header, never today's unpacking or world schema, so a career this version can no longer read is still recognized. The reset reports how many careers it cleared and the client shows one notice. Each active checkpoint and parked game is classified independently; unknown/future or corrupt unclassified data stays available for recovery. An interrupted parked cleanup is journaled and retried. Device profile, strategy library, preferences and unrelated storage survive. Legacy file imports remain refused.

Portable fixtures keep the four historical scenarios and their original explicit authority unchanged. `currentRules: true` selects the active founding defaults; marked `announced-player` and `financial-conflict` setups provide deterministic synthetic inputs. Their actual encouragement, joint approval, manual events and mediation use normal commands. The current-rule expected facts also include responsibilities, retained own-person careers, joint proposals and fixed-deadline commitments; `tests/fixtures/run.ts` defines this portable projection.

Worker inspection may return only world identity/revision to the storage coordinator after complete decode/schema/reference validation. A single immutable validated candidate, keyed by the complete raw checkpoint string, can be consumed by activation; it is discarded before becoming live state. Public standalone unpackers retain strict validation. The private load path validates compact scalar shapes/dimensions/references, then validates expanded career facts once as part of the complete world instead of copying them through duplicate intermediate schemas.

Career representation version 3 uses the unchanged version-two relationship grammar and scalar codebooks, but groups stored person rows by descending employment count, then coaching-entry year (or birth year + 1000), then raw UTF-16 person ID. Its required `order` Base64 stream maps each stored row to its original registry index using signed zigzag LEB128 deltas from the previous index, initially zero. Each value uses at most three bytes; the known row count bounds input before allocation. Canonical Base64, minimal varints, exact stream consumption and the complete permutation are checked. This must be a complete permutation of 0 through count−1; missing, duplicate, fractional, negative or out-of-range indexes fail before activation. The reader restores the original registry order before returning people, preserving iteration-sensitive simulation behavior and every nested job/mentor array. Version 2 has no order metadata and retains its original stored-row order; version 1 remains supported. Future versions fail as compatibility errors.

In version 3, person columns 14–17 (intention, retirement, coaching, management) each store `[scalarColumns, presenceRuns]`, with widths 7/5/5/5. Runs alternate absent/present starting absent; only the first run may be zero, and runs must cover the exact person count. Each scalar column has exactly the number of present profiles. The reader checks counts/dimensions before expansion, restores complete profiles before resolving relationship/date references, then performs the existing strict scalar/person/world validation. Nulls, booleans, arbitrary fractions and original nested array order remain exact. Version 2 continues using its original inline profile rows.
