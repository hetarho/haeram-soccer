# Continuous match and aggregate-result contract

This is an implementation specification for the follow-up tasks beginning at T272. It does not describe completed functionality. Gameplay policy belongs to MATCH r15, WEB r94, HIST r16, SAVE r50 and ARCH r16.

## Ownership and sequencing

- Existing task files and their accepted interfaces remain unchanged. Shared implementation begins after T255, the identity feature's final gate. T272 may build measurement tooling independently; capture its actual pre-change baseline on the source after T255 and before new football changes.
- The work is standalone planning, with no assignments added to an active work-group lane. Every new task uses `lane:-`; exploration and its dependent tasks stay in the main session.
- T273 owns shared DTOs, compatibility metadata and validators; T279 owns the aggregate kernel and input adapter; T282 owns the exact compact representation. Consumers use those contracts rather than parallel private variants.
- The full-model production activation remains disabled until the combined release gate. Tests and measurement commands may request the candidate model explicitly. This is an internal release switch, not a player control or a runtime speed-dependent fallback.

## Candidate model and safe activation

- Define one `MATCH_MODEL_REVISION` in `packages/contracts/src/match-model.ts`, initially `continuous-aggregate-1`.
- `World.matchModel` is optional for supported older worlds. When present it contains the recognized revision, activation game date/revision and first tracked boundary for the new counters. Missing metadata means the pre-feature model; unknown future revisions are typed compatibility failures.
- A full-model `MatchRecord` carries its model revision and supplies the existing metrics, xG, TD, PD, participation/lineCounts, incidents, added-time and applicable knockout fields. Older records retain their actual optional-field presence. `FullMatchRecord` refines the existing DTO; it does not globally require new fields on historical records.
- Add candidate-only adapters to detailed and aggregate processing while the release switch is off. A supported writer activates once at a safe boundary; no unsettled revealed playback is replaced, no settled fixture is replayed and no monetary or personnel fact is changed by the metadata upgrade.
- Keep gameplay rules 4.0.0 compatibility. T273 defines `FULL_MODEL_CHECKPOINT_SCHEMA` as the next container after the identity feature's container; T282 implements its codec. Select that container only for candidate-model metadata/aggregates after the codec is available; ordinary unactivated worlds keep the existing writer format. Retain older readers and refuse future containers. Never classify a supported 4.0.0 save as resettable legacy data.
- Activation uses the existing worker writer/commit protocol. Read-only and failed-write paths preserve source data and exportable memory. The final gate enables the release switch only after all required evidence passes.

## One match-time coordinate

- Engine coordinates remain metres on the existing pitch. Every recorded knot has an absolute elapsed match time, with a period identifier. All movement bounds and action durations are expressed against match seconds.
- Preserve `MatchMotionSample.elapsedSeconds`. Extend frames with an explicit start time and a parallel time array for ball-track points; lengths, monotonicity and period membership are validated. Keep legacy frame decoding when explicit times are absent. Old `pace` values remain readable but candidate frames set a neutral pace and the new clock ignores situation weights.
- Evaluate player and ball paths by their timestamps, not an assumed equal sample interval. Include semantic knots at a kick, arrival, reception, tackle, restart placement and change of intention. Crossing a minute does not reset a trajectory. Never interpolate across a declared period/seek boundary.
- T274 defines shared `GRID_MOVEMENT_CONFIG` and `GRID_BALL_CONFIG` once. Start the ball model with pass/turnover speed 20 m per match second, restart 18, shot 30 and maximum 40; these are implementation defaults to measure, not a claim of researched football constants. Player top speed reuses the existing pace/fatigue calculation; initial acceleration is 4 m/s², braking 6 m/s² and maximum turn 180 degrees per match second. T278 may tune the shared configuration against the unchanged targets.
- Schedule the action long enough for its physical route. Preparatory dead time contains player relocation and ball retrieval; the kick follows actual arrival. Do not move a taker, marker, receiver or set-piece participant directly to an unrelated location or shorten a flight to meet a preselected deadline.
- T275 maps elapsed match time with `WATCH_MINUTE_MS` and selected speed, preserves the current position when speed changes, and supports old saved replays. Presentation never advances or reruns the engine.

## Intentions and team reactions

- Add transient `GridPlayer.intention`: kind, target, optional teammate/opponent reference, start time, expiry and cancellation/priority reason. It is match-local, not a new player attribute or a career DTO. Existing run state becomes a compatible view of that intention rather than an independent competing planner.
- T276 owns the common intention lifecycle and priority order: unavailable/exit, restart assignment, immediate defensive danger, committed receiving/carrying action, then tactical support/run/mark/cover/recovery. A reasoned event can interrupt an intention; an ordinary update preserves it while feasible.
- T277 owns side-level assignment of pressing, covering and support jobs using a shared snapshot, then individual role/trait choices. Stable roster IDs break ties. No processing-order advantage or repeated per-render random decisions is allowed.
- The carrier consumes current teammate intentions in `decide.ts`. Record the active target, state and relevant partner in observation traces so the renderer and inspector show the same choice the engine uses. Existing four tactics, substitutions and manager authority remain intact.

## Full aggregate facts

- T279 defines `AggregateInput` and `AggregateTeamFacts` in `packages/engine/src/aggregate/types.ts`, plus `buildAggregateInput` in `aggregate/input.ts`. Consume the existing prepared strength, lineups, tactic effects and effective skills; do not create a second strength formula. Adapt the existing prepared match at dispatch rather than generating another world or another roster.
- `generateTeamFacts(input, streams, participation)` creates coupled team facts: possession/time allocation, passing flows between coarse cells, attempts/completions, chances/shots with place and quality, set pieces, turnovers and advanced counters. It never steps all players through space or loops through every match minute.
- Generate a compact internal ledger sufficient to derive the required numeric definitions. It may group actions and use coarse-cell flows; it is not an NPC frame trace and is discarded after complete result construction and ordinary settlement. xG, xA, xT, entries and pass classifications come from that shared ledger, not unrelated independent totals.
- T280 defines `planParticipation` and `attributePlayerFacts`, then `simulateAggregate`. Plan legal era-dependent starters, substitutions, dismissals and injuries before final team production; pass their on-pitch intervals/strength effects to the kernel. Allocate only to eligible participants, by role and effective attributes, preserving exact team/player sums under the defined metrics.
- Use separately named seeded streams for the candidate model, fixture and decision family. An observer, stat query, command count or unordered map iteration cannot change a draw. Reusing earlier named world streams must not perturb unrelated recruitment or finances.
- For extra time, extend the aggregate period facts and participation intervals under the existing tie rule. Use the existing taker/keeper shootout rules, not a winner coin flip. Regulation and shootout scores remain distinct.
- `validateFullMatchRecord` is shared by detailed and aggregate adapters. It checks all field widths/presence, contributions, classifications, time legality and derived totals. Violations fail before settlement; clamping unrelated outputs until they fit is not an acceptable replacement for coherent generation.

## Current-season aggregates and retention

- T273 defines `NpcSeasonStats` for one season: a tracking boundary, competition/club totals and compact participant identity plus per-club contributions. Preserve departed contributors until that season closes. Use stable IDs; do not clone full generated `Player` objects into the persistent ledger.
- T281 owns one settlement reducer used by league, cup, playoff and European paths. It updates full current-season aggregates, existing scorers/availability/Elo and existing retained-person facts exactly once, keyed by the fixture. A settled or duplicate command is a no-op for accumulation.
- T282 owns packing for the new DTO and model/coverage metadata. Width/presence tables are versioned and bounded; sparse columns and shared identity/competition indexes restore the exact canonical DTO. Missing, zero and untracked are distinct. Wrong dimensions, references or future metadata fail before activation.
- Own matches and material retain their current history lifetimes and frozen kit appearances. NPC full match records are transient; after settlement the new ledger retains current-season aggregates, while existing older NPC archive/person scope remains unchanged. Do not retain all NPC maps or match traces to achieve numerical parity.
- T283 extends existing projections/comparison views. It does not add a world-simulation settings screen. Fully tracked generated counters use the ordinary metric labels; earlier missing periods expose their tracking boundary and sample size.

## Shared contracts (T273)

The names later tasks consume; each is defined once.

- `packages/contracts/src/match-model.ts`: `MATCH_MODEL_REVISION` (`continuous-aggregate-1`), `MATCH_MODEL_REVISIONS` and `isMatchModelRevision`; `MatchModelState` (`revision`, `activated` game date and world revision, `trackedFrom` `{ year, day, round }` boundary, `coverage` `founding | activation`) with the strict `matchModelStateSchema`; `activeMatchModel(world)`, the one reader of a world's model (absent = pre-feature model).
- `World.matchModel?` and `World.npcSeason?` (`NpcSeasonStats`: season `year`, `model`, `trackedFrom`, and per competition (`kind`, `groupKey`) club totals — `matches`, `metrics` (M widths), `detail` (TD), `xg`/`xga` in hundredths — and players under stable `id`/`name`/`position` with per-club `NpcContribution` rows of `appearances`, `metrics`, `detail`). Both are optional and absent until activation; nothing writes them yet.
- `MatchRecord.model?` and `FullMatchRecord`, which requires `model`, `xg`, `detail`, `incidents` (an empty list when nothing happened, so presence says the path tracks incidents), `lineCounts`, `added` and `detail` on every line. Older records keep their optional fields; Metrics/TD/PD indexes and units are unchanged.
- Time coordinate: `MatchFrame.startSeconds?` and `MatchFrame.ballTimes?` (elapsed match seconds, aligned with `ballTrack`), `NEUTRAL_FRAME_PACE` for candidate frames, and `frameTimeIssues(frames)`: explicit times on all frames or none, contiguous minutes within a period (a gap only at a period boundary, never a backward period), ball knots aligned and strictly increasing inside their minute, motion samples ordered inside it. Legacy frames without times are left alone.
- Intentions: `PlayerMotion.intention?: IntentionObservation` (`kind` from `INTENTION_KINDS`, `priority` from `INTENTION_PRIORITIES` highest first, `target`, optional `teammate`/`opponent`, `since`/`until` in elapsed seconds, `ended` from `INTENTION_ENDS`). Observation only; T276 owns `GridPlayer.intention`.
- Compatibility: `assertMatchModelFormat(value)`, a bounded preflight that throws `SaveCompatibilityError` for an unknown `matchModel.revision`, `npcSeason.model` or own-record `model` string; `FULL_MODEL_CHECKPOINT_SCHEMA` (`3`) in `versions.ts`, declared but not yet read or written (docs/SAVE-FORMAT.md). `apps/web/src/runtime/protocol.ts` `worldMetadataOf(world)` returns `{ id, revision, matchModel? }` with a validated copy of supported metadata and the typed failure for a future one, without activating or changing the world.
- `packages/engine/src/match-model.ts`: `MATCH_MODEL_RELEASE` (`enabled: false`, the internal release switch) and `validateFullMatchRecord(record)`, the exact check both paths share — all full fields at their widths as non-negative integers, score = goals, successes within attempts, MATCH-13's shot-class and key-pass orderings, each side's lines reconciling exactly with its team row (Metrics before minutes, every PD counter named like a TD one, fouls won against the opponent's fouls, xG within each shot's rounding), line minutes 1…match length and at most eleven times it per side, lines within 11 + the era's substitutions, incidents naming the side's lines in time order without a player acting after leaving and agreeing with the card counters, and the period/shoot-out shape. It returns the failures and never repairs; `assertFullMatchRecord` throws them before settlement. On 200 own-world fixtures of the post-T255 grid every record passed it.
- `buildGridSetup(world, fixture, { model })` takes an explicit candidate revision for tests and measurements; otherwise `GridSetup.model` is `activeMatchModel(world)`. It draws nothing.

## Measurement registry and release evidence

- T272 creates `scripts/lib/match-parity.ts` with the complete metric registry, units, invariant definitions, condition matrix, independently named training/validation seeds and all test budgets. Existing `Metrics`, TD and PD indexes remain authoritative; a new index without a registry entry fails coverage validation.
- `PARITY_CONFIG` defines the numeric comparison settings once from MATCH-28. Treat a metric as rare by explicit registry classification; use an equivalence interval that fits its declared margin. Constant-reference variables and unidentifiable correlations are reported explicitly, not divided by zero or silently passed. Round counters in their canonical units before reconciliation.
- `CORPUS_CONFIG` initially uses 600 calibration fixtures per core condition; calibration/pilot variance determines a predeclared validation size, initially at least 4,000 and at most 100,000 fixtures per condition. Rare-event conditions begin with 10,000. Freeze candidate parameters and the validation sample before evaluating it; further evaluations use fresh held-out seeds under a declared uncertainty procedure. These settings are not proof of sufficient power; an unresolved interval remains insufficient. Cover all strength-gap buckets already used by `calibrate.ts`, every tactic pairing, tier bands and era/knockout rules without claiming an unmeasured Cartesian product passed.
- The report distinguishes absolute intended target bands, detailed-versus-aggregate equivalence, exact consistency and runtime/capacity results. Detailed-engine defects are named and fixed against intended targets; the aggregate model does not learn their error as a target.
- T278 calibrates the changed detailed engine. T284 calibrates aggregate equivalence with held-out seeds and checks season distributions. T285 profiles and optimizes cost without weakening the registry or football rules. Each is a timeboxed exploration whose completion records residual failures; only T286 can declare the full model ready.
- `PERFORMANCE_CONFIG` consumes ARCH-31's paired relative budgets and existing browser/storage limits. Record fingerprints, seeds, toolchain, machine, repetitions, timing components and actual check outcomes. Large measurement runs are CLI artifacts; unit tests use small independent fixtures.
- T286 runs final combined parity and the unchanged local century/browser benchmarks, uses the batch/CI evidence required by ARCH-30 and verifies prospective activation and rollback refusal. An unmet accuracy or capacity gate leaves activation disabled and produces a concrete follow-up; no passing result is invented from a timebox exit.

## Measurement tooling (T272)

`scripts/lib/match-parity.ts` is the one place later tasks read names from; nothing under `apps/` or `packages/` imports it. `MATCH_PARITY_VERSION` changes with any entry, band, condition, partition, size or tolerance.

- `METRIC_REGISTRY` is generated from the contracts' `M` (team and player rows), `TD` and `PD` maps, so every index has exactly one entry with its stored and canonical unit (`xg-hundredths` → xG ×0.01, `xt-thousandths` → xT ×0.001), its rare-event class and its player-to-team reconciliation (exact, within per-shot rounding for xG, or at most). It adds team xG, participation (lines, minutes), one entry per incident kind (a new `Incident['kind']` fails the type check), outcomes, ratios with their recorded denominators (PPDA and field tilt read the opponent's or both sides' counters) and season/career measures. `validateRegistry` rejects an uncovered, doubled or unknown index and dangling references. The player row's possession slot is registered as not applicable rather than read as zero.
- `TARGET_BANDS` holds MATCH-23's rows and MATCH-1's added time, each reading the record or the grid's diagnostics; `OUTCOME_TARGET`/`outcomeTarget` copy MATCH-2's Elo curve from `scripts/calibrate.ts`, and `buildOutcomeTargetReport` records 90-minute W/D/L per calibrate.ts gap bucket against it with the mean absolute error over −10…+40. MATCH-2 sets no tolerance there, so that report measures and never passes; a sample without a `gap` makes it missing. `INVARIANTS` are the exact MATCH-13/19/27 rules: score equals goals, row widths and all-or-none detail, successes within attempts, player rows reconciling with team rows, minutes, xG against shots, incidents (order, roster, dismissal once, era substitution limits, injury-only substitutions) agreeing with the card counters, and period/shoot-out shape. `condition-rules` reads the sample's declared condition, and an unknown condition is refused. It fails a record in four cases: extra time or a shoot-out in a league fixture; any metric the condition rules out that the record still carries; under a tie's `decide` rule (with `isLevel`), extra time that does not come exactly when the tie is level after 90 minutes; and a shoot-out that does not come exactly when the tie is still level after extra time. The knockout conditions declare cup fixtures. A record lacking what a rule reads is `unsupported`, never a pass, which includes an untracked incident list under an era without substitutions.
- `PARITY_CONFIG` carries MATCH-28's margins once. Intervals are deterministic: cluster-robust (by match) normal intervals for means, DKW bounds for the Kolmogorov distance, Newcombe for outcome-rate differences, Poisson log intervals for rare-event rate ratios, Zou/Fisher for correlations, delta-method ratio-of-sums and order-statistic medians for target bands. Only `equivalent` (path comparison) and `inside` (target band) pass. `different`, `violated`, `insufficient`, `underpowered` (fewer than 30 matches, or a rare-event interval that has not resolved with fewer events than `requiredRareEvents()`), `unidentifiable`, `missing` and `undefined` (no denominator) are reported as such. An interval that overlaps zero but leaves the margin is `insufficient`. Following MATCH-28 (r15), a metric both paths hold at the same value is `equivalent` by its zero difference and carries `constant: true`. A reference without spread otherwise keeps its margin of 5% of its mean: a candidate held at another value, or whose interval leaves that margin, is `different`. A reference constant at 0 has a margin of 0 that no interval fits, so it resolves only a difference and is otherwise `insufficient`. A rare event with no events on either path is the same equal constant at 0 once each path has 30 matches; that never makes it not applicable. Rare events compare rates per match, so paths that field different numbers of player lines compare the same thing.
- Each condition declares `level` (match conditions compare match metrics, season conditions the season measures) and `notApplicable`. `ruleExclusions` derives the latter from the condition's own rules only: extra time and shoot-outs where no tie must produce a winner (MATCH-6), and substitutions in an era that allows none (MATCH-20, before 1965). `buildEquivalenceReport({ condition, … })` refuses samples drawn under another condition. It reports those metrics as `not-applicable` with their rule and keeps them out of the verdict. If a path records one anyway, it is `violated` instead, its reason names the rule and the counts, and it blocks. The report lists `constants`, `notApplicable` and `blocking`. `passed` is true only when nothing blocks.
- `CORPUS_CONFIG` declares the core condition and one-factor families around it (calibrate.ts's gap buckets, all 16 tactic pairings, tier bands, fatigue, era years, knockout rules, rare-event and season families) without claiming their product. The core condition names its worlds, founding input, pair order, fixture and tactic assignment: each club plays its own tactic, the only assignment both existing paths support, whereas `scripts/grid-bands.ts` rotates all four tactics by override, so its band readings are not the core condition's. `corpusFixtureId(partition, condition, index, round)` puts the partition into the fixture id, so every named match stream differs between calibration and validation; a later evaluation takes `round` + 1.
- `validationSize(pilotSd, margin)` gives the predeclared size in matches per path between 4,000 and 100,000. `pilotSd` is `clusterSpread` of the pilot's observations: the spread of per-match means, so a metric read twice a match (both sides) or once per player line carries its design effect. The size makes the 95% interval fit the margin with probability `PARITY_CONFIG.power` (0.8) when the paths agree: the power term is the two-sided quantile at (1 + power)/2. It reports the power the clamped size achieves, and `sufficient` is false when even 100,000 falls short. Example: a 3-point outcome margin at p = 0.5 needs 5,838 matches a path. For rare events the rate ratio's interval alone decides; there is no separate count gate. `requiredRareEvents()` is the fewest events each path must expect for the comparison to say `equivalent` with that power when the paths agree. It is solved exactly over Poisson counts with the comparison's own verdict on the asymmetric [0.8, 1.2] bounds, and comes to 536. `rareComparisonPower(expected)` gives that probability for any expected count, for example 0.799 at 534.
- A condition's sizes cover every metric it judges. `calibrationSize(condition)` is 600 matches, or `rarePerCondition` (10,000) for a rare-family condition. `conditionValidationSize(pilotNeeds(referencePilot, condition))` is the largest need, clamped to 4,000–100,000. Each judged mean or proportion needs its `validationSize`, and each judged rare metric needs `requiredRareEvents()` over its pilot events per match (an event at 0.05 a match needs 10,720). At that size the limiting metric's own comparison passes with the declared power when the paths agree, while the other metrics, with smaller needs, pass with more. A metric the condition rules out needs nothing, nor does one constant in the pilot, which the equal-constant rule judges. A rare metric with no pilot events is listed `unsized`. `sufficient` is false when any need passes 100,000. The runner records this for the core pilot as `pilotSizing`.
- `PERFORMANCE_CONFIG` names the timing components and their categories (preparation, computation, observation, settlement, season, codec), ARCH-31's 0.5 and 0.8 budgets, the two century profiles and the unchanged browser/storage limits. `buildPerformanceReport` keeps codec time out of every engine total; `comparePerformance` computes the gates only for runs on the same machine, toolchain and worlds and never treats a provisional run as release evidence. The runner checks each century profile's final checkpoint against `storage.checkpointBytes`. The browser budgets are declared for T286's gate only, because `scripts/first-play.mjs` enforces them on a served production build and this runner builds nothing.
- Samples are `{ record, diagnostics?, incidentsTracked, condition, gap? }`. A grid record omits `incidents` when none happened, so the producer states whether the path tracks them; T273's DTO should make that presence explicit.

### Baseline runner

`pnpm exec tsx scripts/match-model-baseline.ts [--smoke] [--out FILE] [--fixtures N] [--seasons N] [--pilot N]` (default output `docs/benchmarks/match-model-baseline.json`; full mode 200 timed fixtures per path, 100 seasons per century profile, a 600-match pilot). It times, separately: preparation (`prepareMatch`, `buildGridSetup`), whole fixture processing on the summary path (`simulateMatch`, with and without named lines) and on the grid (own and own-league fixtures of the `release-century-baseline` world), observed play and frame building, record settlement on a copy of the world (each fixture once), complete seasons of both century profiles (the active-management actions as `scripts/benchmark.ts` runs them) and the checkpoint codec. It records whether repeated and observed runs settle identical records (→ARCH-5, MATCH-7). The pilot plays the core condition on the grid and on the summary path through the coverage, target, outcome-curve, invariant and equivalence reports. The runner reads `OWN_LEAGUE_ENGINE` without changing it, touches no release switch, and measures a candidate only when `packages/engine/src/index` exports `simulateAggregate(world, fixture) → { record }` (it also records `MATCH_MODEL_REVISION` once `packages/contracts/src/match-model.ts` exists). The report records the source fingerprint (sha256 over the git-listed files under `packages`, `apps/web/src/adapters`, `scripts` and the lockfile/configs), dirty state, toolchain, machine, seeds, conditions and partitions, and refuses to finish if the source changed during the run.

To pair a baseline with a candidate, run the same runner on one idle machine with the pinned Node release, back to back:

1. `git worktree add ../haeram-baseline <post-T255 commit before new football changes>`; in it `pnpm install --frozen-lockfile`. If that commit predates this runner, copy `scripts/match-model-baseline.ts` and `scripts/lib/match-parity.ts` in unchanged (the fingerprint then includes them).
2. In the baseline worktree: `pnpm exec tsx scripts/match-model-baseline.ts --out .tmp/match-model-baseline.json`.
3. In the candidate checkout: the same command with its own `--out`.
4. Compare the two reports' `provenance` and `performance` with `comparePerformance`; a mismatch in machine, toolchain or worlds makes the result context only.

The committed `docs/benchmarks/match-model-baseline.json` is T273's pre-change baseline: the full-mode runner on the clean post-T255 source `9f695530` (fingerprint `64c07633…`, Intel Xeon Silver 4214, Node v24.12.0), captured before any T273 edit, with 200 timed fixtures per path and the 600-match pilot but 20 seasons per century profile (`--seasons 20`) instead of 100, because the capturing session could not run a command longer than 10 minutes. Medians: summary fixture 0.194 ms, grid fixture 87.4 ms, NPC settlement 0.026 ms, season 11.37 s (baseline) and 11.61 s (active management); repeated and observed runs settled identical records. It stays `provisional` and `releaseEvidence: false`: the paired release comparison reruns this source back to back with the candidate under the steps above.
