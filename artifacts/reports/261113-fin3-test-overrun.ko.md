## 왜 이렇게 됐는가

### 1. 실패가 난 부분 대신 전체를 다시 실행했다

초기에는 변경된 재정 정책에 맞지 않는 기존 기대값과 시간 초과가 섞여 있었습니다. 이를 분리해 실패 파일과 영향 범위부터 확인해야 했습니다. 일부는 실제로 그렇게 확인했지만, 확인 후에도 전체 관문을 다시 시작했습니다. 이미 통과한 수천 개 검사를 재실행하는 비용을 통제하지 못했습니다.

`gusta`/ARCH의 최종 관문 절차를 기계적으로 반복하는 근거로 삼았습니다. 변경 범위, 실패 성격, 기존 성공 증거와 재실행 비용을 함께 판단하지 않은 것이 문제였습니다. 규칙이 있었다는 사실이 이 반복 판단의 정당화가 되지는 않습니다.

### 2. 재정 요청을 별도 관전 지연 문제에 묶었다

3회차부터는 474개 파일이 모두 통과했고, 브라우저도 332개가 통과했습니다. 남은 것은 관전 시작 3초 검사 하나였습니다. 사용자 요청의 중심인 투자 여력과 파산 기준 검증과 분리해 처리했어야 했습니다.

대신 병렬 실행 수를 5개에서 3개, 다시 1개로 줄이고 전체를 재실행했습니다. 첫 1분 영상을 먼저 전달하는 관전 보완 코드까지 추가했습니다(`9769ffe9`, 13:16:53). 단독 실행 성공은 있었지만 완전한 전체 성공으로 이어졌다고 확인하지 못했습니다. **13:16:53 이후 중단 처리 시각까지 약 4시간 35분 동안, 내가 새로 추가한 제품 코드 없이 재검증과 통합을 반복했습니다.**

### 3. 같은 checkout에서 실행 중인 검사와 다른 편집을 격리하지 않았다

관전 속도를 12초에서 18초로 바꾸는 별도 작업이 5회차 실행 중 들어왔습니다. 먼저 로드된 코드와 나중에 읽힌 테스트가 달라져 5개 검사가 실패했고, 실행기는 `stale: true`로 판정했습니다. 별도 작업 공간의 고정 커밋으로 처음부터 검사했다면 피할 수 있었습니다. 이후에는 별도 worktree로 옮겼습니다.

### 4. 후보 고정 전에 최신 원격 통합을 확인하지 않았다

원격 기획 보완 `3e83cf97`은 **14:37:55**에 이미 만들어져 있었습니다. 6회차는 **15:15:05**에 시작했으므로 시작 전 통합할 수 있었습니다. 이 확인을 빠뜨린 채 81분 넘게 실행한 뒤에야 발견했습니다.

제품 코드는 같고 별도 월드 선수 기획 문서가 달라진 상황이었지만, 내가 적용한 반영 절차에서는 SSOT 병합 후 후보를 다시 검증하도록 처리했습니다. 6회차를 중단하고 7회차에서 같은 제품 코드와 이미 통과한 검사들을 다시 실행했습니다. 사전 동기화 누락과 문서 변경의 영향 범위를 과대 적용한 판단이 함께 시간을 늘렸습니다.

### 5. 수동 회복에 종료 기준을 두지 않았다

자동 실행기의 재시도 상한을 수동 회복의 상한으로 적용하지 않으면서, 별도의 시간·횟수·실패 범위 축소 기준도 두지 않았습니다. 반복 실행이 실제 사용자 목표를 얼마나 더 확인하는지 재평가하지 않고 다음 전체 실행을 시작했습니다. 결과적으로 기능 구현보다 검증 절차 유지가 우선됐습니다.

## 재발 방지 제안

아래는 제안이며, 이번 요청에서 프로젝트의 검사 기준이나 CI 설정을 임의로 바꾸지는 않았습니다.

1. 전체 관문은 통합 후보가 고정된 뒤 한 번 실행합니다. 실패 후에는 실패 사례와 실제 변경 범위부터 확인합니다.
2. 동일 제품 코드·테스트·설정의 성공 증거를 재사용할 수 있는 기준을 정하고, 문서 전용 변경은 문서 정합성으로 확인합니다.
3. 짧은 지연 성능 검사는 일반 병렬 화면 검사와 별도 실행해, 한 사례 때문에 모든 화면을 순차 재실행하지 않게 합니다.
4. 공유 checkout의 HEAD를 검사 도중 바꾸지 않도록 분리된 작업 공간을 사용합니다. 후보 고정 전에 원격 fetch와 병합 완료를 확인합니다.
5. 수동 회복도 시간·횟수·사용자 요청과의 관련성을 기준으로 중단·분리합니다. 범위 밖 문제와 미완료 검증을 즉시 보고하며, 끝없는 전체 재실행으로 바꾸지 않습니다.
